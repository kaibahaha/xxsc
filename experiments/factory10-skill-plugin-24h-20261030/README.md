## Git 交付契约
每轮在 rounds/R01 至 rounds/R24 目录下创建：
- WORKBUDDY_REPORT.md：WorkBuddy 实际返回的报告正文，注明Job ID、运行结果、工具证据；不得替未完成报告编造。
- CHATGPT_AUDIT.md：ChatGPT 独立研究、逐项事实核验与评分；应包含是否真实核对来源、插件/Skill是否确实存在、安装/授权/费用区分、五个贴合工厂规划的可操作实战案例、风险与建议。
- STATUS.md：本轮时间、工厂、任务状态、Git commit/回读状态、失败与补交策略。

对每一工厂，至少对比 WorkBuddy 插件/Skill 市场和 ChatGPT 已连接应用中的匹配能力；输出优先级、工具使用技巧、典型步骤、依赖条件，并写明哪些是未验证候选。WorkBuddy 应提供五个具体实战案例；ChatGPT 独立检查或补充案例。

## 审计评分（总分100）
- 来源与事实证据 25
- 工厂战略契合度 20
- Skill/Plugin 可执行性与具体使用技巧 20
- 五个实战案例的可复现性 20
- 风险、成本、限制及真实性 15
未取得 WorkBuddy 完整研究报告时不得伪造评分，标记 PENDING/FAILED 并在后续轮次补交。

## 安全与防重
- 每轮采用唯一回合编号并对照 Git 文件回读；每个阶段逐项记录实际状态。
- 不安装插件、不替用户授权外部平台、不读取/提交密钥、不切换 WorkBuddy 模型、不取消别的任务。
- 任务超时或排队时先记录 job_id，后续轮次先核验待交付，再推进当轮；不得并发重复提交同一回合。
- 写入仅限此分支此目录；不触碰其他工厂项目。
- 使用真实 GitHub connector 写入及回读；任何写入失败要明确报告，不能宣称成功。

## V2.0 增量规则（2026-10-30）：同厂复盘、跨厂学习、自适应研究

> 本节补充原协议；不得改变R01–R24轮次、固定F1–F10顺序、原100分五维权重、Git分支及只读权限边界。

### A. 同工厂第二遍必须进行“有针对性的整改研究”
- **R01–R10（第一圈）**：采集基线、完整评分及五例评价，每轮沉淀可迁移的研究方法；无同厂历史时标注BASELINE。
- **R11–R20（第二圈）**：在给WorkBuddy派单前，ChatGPT先回读同工厂R-10的 `WORKBUDDY_REPORT.md`、`CHATGPT_AUDIT.md`、`STATUS.md`。逐条提取其事实错误、遗漏、未经验证的命令、Skill/插件有效性缺口、成本权限风险、五个案例不足及评分细项，形成新一轮可执行整改指令。**必须把详细反馈真正写入WorkBuddy的MCP prompt**，不能只发送Git链接（WorkBuddy云端未必能读取Git）。
- **R21–R24（第三圈）**：分别读取同工厂R-20和R-10两次历史报告，区分已修复、反复出现和新出现的问题，进行第三次针对性优化。
- 同厂历史结果不全时，先凭Job ID追取并补交；确实不可取得则标注 `MISSING_BASELINE`，说明不可比较部分，不能捏造历史评价。

### B. 递交WorkBuddy的反馈包（每轮记录 `FEEDBACK_TO_BUDDY.md`）
反馈必须有如下可追溯字段：
1. 基线：同厂历史轮次、Job ID、报告与审计Git路径、总分、五维分数。
2. 保留优点：可靠证据与值得重复的方法。
3. 整改事项：至少3项具体可行动缺陷（问题原句/实证、原因、修复动作、P0/P1/P2优先级、核验命令/来源和预期验收证据）。
4. 五个实战案例逐案反馈：补足可复现的目标、输入、命令/操作、具体输出、边界测试、失败回滚、时间和成本；说明保留、重做或替换的原因。
5. 当轮强化目标、禁止再犯的推断，以及可比较的质量改善指标。
6. 实际发给WorkBuddy的研究委托必须包括上述实质内容，且要求WorkBuddy输出“问题→修订→证据→已修复/未修复”追踪表。

### C. 跨工厂逐轮自适应（每轮记录 `ADAPTATION.md`）
- 读取最近1–3轮**已经完成**的WorkBuddy报告和ChatGPT审计，提取通用研究问题（如市场缓存误认已装、Agent API与LLM网关混淆、虚构CLI、缺失真实操作证据、预算与OAuth混淆），以及有证据支持的最佳做法。
- ChatGPT每轮最多选择1–3个可检验的方法调整：例如必须附命令help证据、区分同源官方连接器与功能类比、五例增加异常测试/成本估计/回滚验收、先读官方文档再做结论。
- 在 `ADAPTATION.md` 写清：观察事实→原因假设→明确变更→真实注入给WorkBuddy的prompt内容→下一轮测试指标→后续效果(有效/无效/证据不足)。
- 严禁机械复制上一工厂的业务内容；仅迁移经证实有价值的研究方法，所有修改严格保持既定安全、权限和调度边界。

### D. 改进成效的审计与纵向比较
- **100分总分保持不变**：来源证据25、战略契合20、使用技巧20、五案例20、风险真实性15；不放宽评分以制造上升趋势。
- `CHATGPT_AUDIT.md` 必须新增整改检查表：每条反馈项的回应位置、证据、已解决/部分解决/未解决/无法判断；评估最新增加的方法要求是否实际执行。
- 自R11起报告同厂上次与本次总分和五维分差Δ，比较严重错误复发、案例可复现性和证据等级；同时注明任务难度或证据覆盖不同造成的不可比性。
- 对最近1–3轮方法调整需持续观察，并用后续实际报告验证是否降低误差或提升证据质量。资料不完整时用 `NOT_EVALUABLE`，不可伪造改进百分比。

### E. Git持久化与调度防重
每轮在 `rounds/Rxx/` 中保留/建立 `WORKBUDDY_REPORT.md`、`CHATGPT_AUDIT.md`、`STATUS.md`，新增 `FEEDBACK_TO_BUDDY.md` 与 `ADAPTATION.md`。可维护根目录 `ITERATION_LEDGER.md` 汇总轮次、工厂、Job ID、五维评分、主要缺陷、方法迭代、前次同厂分数与改善效果；只可凭Git当前blob SHA读改写回，冲突先合并，不覆盖别轮。
- 每轮只能派单一次，先查已有Git状态与待处理Job；排队/中断时仅记录真实状态，后续追单或确定失败后再按独立防重约定处理。
- 对未完成研究，先交 `STATUS.md` + 可证实的反馈和计划，延迟正式评分与效果评价；不能凭空编造原报告。
- Git每项写入必须回读；报告内容、审计和WorkBuddy收到的反馈要对应。每轮对用户报告：实际轮次、工厂、Job ID、交付状态、质量评分、继承改进、同厂对比与下一轮计划。
- 不安装插件、不开新任务、不切模型、不操作其他分支、不扩大费用或权限；自适应范围**只限下一轮研究指令、方法、证据与验收设计**。
