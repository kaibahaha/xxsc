# 10｜最小实现路线与试运行验收

## 阶段0（现已完成：静态设计，不是部署）
已形成源码对照、中文规则、Git 目录与 JSON Schema、五个定时提示词、示例事件与离线示例校验。**不声称五条定时任务已被更改或 Controller 已连接。**

## 阶段1：只读影子验证
在独立 Git 分支读取相同任务池，模拟 A、B 同时见到 READY 的判断；审计旧 Task 与新协议是否冲突。Controller 未配置原子授租前，CLAIM 只能作为协作提议；没有实际 write 测试不得切现网。

## 阶段2：两 Agent Git 闭环
由已有权限的执行端创建隔离 TASK；A 提出 CLAIM、完成独立稿，B 在实际下一次运行读到 A 的 NOTE 并提交 REVIEW；验证 SHA、事件 ID、回执和两次读取时间。检查不应重复消费 ACK，不得碰旧分支。

## 阶段3：故障注入
模拟重复 event_id、相同任务同时 CLAIM、Git 创建调用超时、BOARD_UNKNOWN、旧 epoch 迟到、测试失败、Work grace 未到和错过一个唤醒；逐项验证状态正确收敛。没有实际运行证据时报告 `NOT_TESTED`。

## 阶段4：五个错峰 Agent
只有在用户允许修改正式定时任务且平台真实支持时才创建/更新排班。记录每个 Agent 实际 schedule_id、工具访问能力、Git branch、写路径白名单、真实唤醒、执行时长和最后 ACK。保留原系统回滚开关，不允许双主 Controller。

## 阶段5：接 WorkBuddy、Codex、Work 和媒体执行
只接入经实测的授权执行与文件通路，Git Hub Webhook/MCP 能否在 ChatGPT 定时环境直接调用特定服务，必须单独证明。移动设备无需本地电脑的前提是所有必要执行端及凭据确实在云端在线。

## 通过条件（候选阈值，非既有成绩）
零重复有效验收；零越权写入；零以“文本应当通过”冒充真实测试；读写失败被显式标 UNKNOWN；模拟 crash 后 ACK 恢复正确；24小时影子运行按实际到期数逐项核对。最后由用户批准 V4.1 从 DRAFT 到 ACTIVE。
