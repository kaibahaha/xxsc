# Agensh-Lite：自组织任务拆解、无人软件工厂与自主评测体系——本轮讨论全量研究归档 V1.0

> **定位**：本文件系统保存本轮专题交流自开始至“评测由Agent设计、在独立沙箱执行、第三方平台是否必需”这一节点的全部与项目有关的论题、澄清、形成的认识及可落地建议。不是微软论文逐字译本，不是现有V4.2的替代架构，更不是已经部署的生产策略。高尔夫、天气及旁人交谈等非项目语音不纳入事实链。
>
> **重要约束**：不把用户提出的有启发性的假设写成微软已证实的机制；不把我们设计的独立QA、Mini Controller、Git收件箱、RSI实验道等写成微软原生功能；不把讨论中的部署设想写成运行成功。

## 0. 如何阅读：四个证据层级

本文每项关键结论按下列标签理解：

- **[M-官方]**：本次重新对照微软公开仓库的README、原始Agent指令、复现说明或评分工具说明所得。
- **[P-项目]**：现有Agensh-Lite V4.2/V4.0归档中的架构共识与工程约束；可能尚未部署。
- **[D-讨论]**：本轮用户与助手交流得出的理解、判断或讨论性方向，并非实验结果。
- **[H-假设] / [R-建议] / [U-待证]**：尚需验证的因果解释、候选技术设计、缺失实证。

涉及百分比，严格区分**百分点**、**相对提升**、**测试用例通过率**、**业务任务完成率**、**Agent有效产出率**；这几者不能互相代替。涉及“已做完”的说法，严格区分提交代码、自检、独立QA、集成验收、产品可用以及真实玩家满意。

## 1. 一页总论：这轮讨论最重要的认识

**[D-讨论] 第一，任务拆解本身不必总由人类完成。** 在足够清晰的总目标、共享状态、可执行工具与协作协议下，Agent能够自主发现缺口、建立子任务、选择工作、分享证据并反复迭代。微软Agensh提供了一个有价值的研究实例：不是由中央总架构师预先向1024个Agent派发1024张工单，而是共同目标下的局部自治、动态发现和异步协作。

**[M-官方] 第二，微软验证的对象有特定边界。** 其主要实验是ProgramBench软件复现任务：观察参考可执行程序的行为、编写替代实现、通过基准测试；1024-Agent规模的55.06%是Pandoc任务最终提交程序的**测试用例通过率**，并不是“1024个Agent做完了55%的子任务”，也不是独立第三方已经完成了工业验收。对一个包含UX、UI、前端、后端、数据库及玩法的Web游戏，不能直接推导“架构一定能自动长出来”。

**[D-讨论] 第三，复杂项目的一级任务规划也可以让Agent协同研究。** 可以将UX/玩法、UI/视觉交互、前端客户端、后端与数据服务等视为候选一级工作域；但这些只是初步工作假设，不是四个互不关联的静态工位。接口、数据模型、集成、系统测试、体验评测、治理本身可以由Agent进一步提出、协商、补充、拆分甚至重组。

**[D-讨论] 第四，评测标准本身也是一个可以自组织研究的工作对象。** 研发Agent、测试设计Agent和评测方法研究Agent均可自组织运转。关键不在于人类必须手写每一条指标，而在于提出标准的人不能未经独立验证就把自己的新标准晋升为正式唯一裁判。

**[R-建议] 第五，“测试主体、执行环境、权威裁决”必须解耦。** Agent可以制定测试并分析失败；独立沙箱/CI Runner执行可重复的客观检查；第三方平台及真实用户反馈可以提供额外独立证据。沙箱不等于第三方，第三方也不自动意味着可信。项目无需为所有测试另建整条生产线。

**[P-项目] 第六，我们与微软的结构差异应该被视为研究变量，而不是劣势定论。** 微软使用事件驱动的协作环境、共享工作区、Mattermost和随轮次注入/更新的共享上下文；我们的ChatGPT定时任务会话往往离散唤醒，优先通过Git持久事件、BOARD投影、INBOX/ACK、HANDOFF重建当前工作事实。聊天历史不担任权威数据库，是有意的架构取舍。

## 2. 本轮专题从开始到现在的讨论脉络（按议题顺序）

| 序号 | 讨论的原始问题 | 当时形成的认识及必须保留的边界 |
|---|---|---|
| 01 | 如何评价新上传的Agensh-Lite V4.2与治理规范？ | 区分微软原版机制和我们追加的Controller、风险QA、Git事件账本、异步接力；V4.2仍属候选架构。 |
| 02 | 新方案的最大亮点是什么？ | 自组织工作循环、CLAIM软认领、短共享FACT/FAIL、消息恢复、提交后回读、独立QA及低成本Lite-M+。 |
| 03 | 微软怎样防抢单、避免冲突、保持协作？ | 共享CLAIM、直接消息协商、合并冲突后同步重测；不等于具备数学意义的严格排他租约。 |
| 04 | Agent领了任务一两小时没进度是不是死机？ | 长任务仍在运行、模型卡住、无进展、失联应分开；心跳、租约、进展证据和超时升级需不同指标。 |
| 05 | ACK是什么、经验教训如何共享？ | ACK是消息消费/处理回执，不是代码验收；FAIL和FACT等短证据能减少重复错误。 |
| 06 | 能否让Agent主动改变团队流程和开新子任务？ | 微软有自主开issue、调整协作与局部角色分工的空间；未证明任意Agent可直接改写全局系统级治理契约。 |
| 07 | 递归自我改进（RSI）是否应走旁路验证？ | 对局部流程变更可历史回放、影子测试、小规模隔离实验，不必复制完整生产工厂；评价标准需独立。 |
| 08 | 微软开源后有多可信？ | 论文+源码+复现脚本提供可审查证据，但作者自己跑出的数据与独立第三方复现不同。欢迎度/星数不等于可靠性。 |
| 09 | 实验到底测什么？ | 多个ProgramBench任务的单Agent/多Agent对照；1024规模仅针对Pandoc任务进行展示，不是1024份预派工单。 |
| 10 | “自集成”是不是提示词原来就暗示过？ | 是：原提示词已经要求PR、合并和冲突复验；**专门集成角色的分化**可以是涌现现象，但集成能力本身并非凭空出现。 |
| 11 | 微软Agent是否保存个人上下文？ | 有Agent本地工作会话、事件和共享上下文；保留/恢复并不等同于全部个人历史永远不丢。我们的定时Agent不应依赖聊天长期记忆。 |
| 12 | 双来源上下文会不会更易污染？ | 存在旧消息、错误FACT与个体偏见风险；不能直接断言微软一定更严重。应该对事实建立可回溯证据、版本和可撤销机制。 |
| 13 | 1024个Agent怎么管理？ | 没有单个总指挥人工盯全部；共享规则、短消息、Git/Gitea与自动测试承担协作闭环。并不等于所有Agent都在高效工作。 |
| 14 | 是因为有上万项任务才需要1024人吗？ | 不是事先给1024人分配成千上万条独立任务；这是对复杂共同目标的探索和动态拆活。 |
| 15 | Pandoc到底是多复杂的任务？ | 在限制条件下重建参考文档转换程序，涉及多输入/输出场景和边界行为；不是具有Web前台的游戏产品。 |
| 16 | 子任务究竟由谁拆、拆到多细？ | 同级Agent自己从未探索的参考行为及现有代码发现工作，开issue、CLAIM、实现；公开基础Prompt无固定每单多少分钟/行/模块的粒度阈值。 |
| 17 | 55.06%到底代表什么？ | 最终Pandoc替代程序在ProgramBench测试集上的通过比例，不是自报任务完成比例；研究团队调用外部基准进行自动化评分，非第三方独立复现认证。 |
| 18 | 至少说明他们搭出了七七八八的系统吗？ | 说明出现可提交且可在部分测试场景运行的系统和自组织协作产物；55%左右的测试通过率不能概括为工业可用率。 |
| 19 | 前端、UI、UX、后端、跨模块API谁设计？ | Pandoc实验不覆盖完整Web产品的这些产品性工作；我们的Web游戏可先做四大候选领域，再动态产生接口、集成和QA工单。 |
| 20 | 能否连一级规划也让Agent自己协商？ | 可以将“该拆成哪四块、是否需要第五块、每块怎么定义”本身作为规划研究任务，而不是先人为冻结所有工单。 |
| 21 | 游戏不像程序复现有唯一客观标准，怎么办？ | 区分技术正确性、跨模块集成、玩法与体验；评测由多指标构成，其中用户体验需要外部证据校准。 |
| 22 | 评测标准能不能也让Agent讨论制定？ | 可以。标准提案、对抗评审、实验验证、正式晋升应独立留痕；不能作者自出题、自改分、自认合格。 |
| 23 | 测试用Agent自己的系统还是沙箱/第三方？ | 测试设计权、执行位置、最终采信权是三个维度。可由Agent产测试，隔离Runner自动运行，第三方/真实玩家按风险补证，不必三选一。 |

这些条目为**问题链索引**，后面逐一给出机制与实践含义，而非将聊天中的所有表述机械视为事实。

## 3. 微软Agensh原版：真正预先给了Agent什么

### 3.1 官方能够直接确认的“公共工作协议”

**[M-官方]** 微软项目README将Agensh描述为“无中央编排者”的自组织多Agent harness。公开的原始提示词位置是 microsoft/Agensh 仓库中的 prompts/agents.txt，其中规定：

1. Gitea上issue #1是总任务；每个Agent可为自己承担的工作区域开issue，PR承载代码贡献。
2. 所有人平权；Agent自己发现待实现区域、自己CLAIM、自己实现、自己验证、自己提交PR并尝试合并，然后寻找下一件事。
3. 用 /opt/pbench/executable 探测尚未复现的参考行为；在相同输入上比较参考程序和自己编译的程序。
4. CLAIM冲突时优先消息协商，特别是同时改同一处代码时使用Mattermost DM。
5. Git合并失败时同步main、重新测试，不能忽略冲突。
6. 重要经验在shared context board发表OBSERVED、FACT、FAIL、CLAIM、PATCH_SUMMARY。短条目配详情按需展开；FAIL特别用于阻止同行重复无效尝试。

**结论**：微软事先规定的是目标、工具、工作循环和协作礼仪，**不是全部子任务的静态WBS（工作分解结构）**。不过称之为“什么也没规定”同样错误；谁可以做什么、在哪里同步、怎么验证、怎样合并，已经是明确的基础组织契约。

### 3.2 子任务粒度：论文/基础提示词没有写死“多大”

**[M-官方]** 基础Prompt没有对每项子任务给出统一的“5分钟/500行/一个API”的固定尺度。实际粒度受可观察的参考行为、局部可验证性、代码边界、与同行冲突概率等影响。Agent先在某一缺口上建立CLAIM，而非等待唯一中心调度员分配完整工作包。

**[H-假设]** 有的Agent因观察到不同参考行为、当前main版本、先前FACT/FAIL、不同时间收到的消息，可能选择不同粒度的任务和不同角色；这可以解释分工差异的一部分。但“每个LLM注意力不同是分工主要因果原因”仍需对照实验验证，不能冒充微软作者已经证明的定律。

**[R-建议]** 面向本项目时，不应将“无限自主开工单”解释为无限扩大范围。建议研究“最小可验收结果、依赖可判定、预计完成时间、单一主要责任、失败可恢复”的粒度指标，让Agent提出分解方案，由协作层检测重叠和依赖风险。

### 3.3 集成不是“无提示词的完全涌现”

**[M-官方]** agents.txt本来就要求每位Agent会push、开PR、merge、遇合并失败重测。因此，“有人会合并代码”是预置能力。论文/README观察到随着规模增长，集成工作流和更专门化的职责逐渐出现，这属于组织行为现象。

**[D-讨论]** 用户对涌现现象的质疑成立：如果基础提示词原本写了集成，必须分清“遵循提示词做集成”与“自发形成分工更明确的集成者”。若要做因果测试，可设置“有集成指令/弱集成指令”“有CLAIM/无CLAIM”的对照；这只是我们提出的实验，不是微软已跑过的反事实实验。

### 3.4 1024个Agent不是1024个固定模块

**[M-官方]** 所有Agent在共同总任务下探索参考程序与工作区，自主找到可做的部分；Gitea issue、CLAIM和消息是不断演化的工单生态。没有证据支持“启动时先创建一万个独立任务”或“人工总架构师给每位Agent分配唯一静态工单”。

**[U-待证]** 具体1024-Agent运行中每小时活跃人数、每人有效贡献、重复工作占比、冲突成本、真实独立子任务数量、代码最终接受率，需要追踪完整实验轨迹，不能用Agent总数或终态测试分数倒算。

### 3.5 时间、环境、消息与上下文机制

**[M-官方]** 微软公开代码/文档给出的运行环境包括Gitea共享仓库、Mattermost消息通道、Shared Context Board和mini-router。个人Agent使用ACP会话延续，事件机制使直接消息与新的Board内容可以在工作回合中传入；环境具备ACK、重试/恢复等基础设施能力。

**边界**：这不能推导为每个Agent的全部私有token历史可跨任意进程崩溃永久保留，也不能推导其共享FACT都由独立程序验证为真。共享上下文越及时，越能纠正错误，但也会更快传播错误；关键问题是来源、版本、冲突处理与可信度，而非“消息数量越多越好”。

## 4. 55.06%到底是什么：消除一系列会话误解

### 4.1 研究任务、软件产物、测试题，三者完全不同

**[M-官方]** 微软把ProgramBench中若干高难度软件复现任务作为实验对象。对于Pandoc这一项，Agent团队需要观察参考程序、利用打包文档和给定工具，在六小时预算中合作编写替代程序。之后由研究者使用ProgramBench的评测工具评价**最终提交的代码**。

“55.06%”的定义是：**该最终提交软件在该基准的测试用例集合上，通过的测试用例比例**（官方评分流程使用规范化去重后的测试身份）。它不表示：
- 1024人中55.06%的人工作有效；
- 自主拆出的100张任务卡有55张完成；
- 55.06%的模块已实现；
- 55.06%的用户认为产品好用；
- 第三方已对Microsoft的结果执行独立认证。

直观类比：一千多名Agent共同交出**一份软件作品**，评测系统用许多输入样例检验作品行为是否符合要求；约55%的判定通过。不能把它简化成“软件已经完成55%的工程量”，不同用例覆盖度和重要性可能很不相同。

### 4.2 官方具体数字（不同口径必须分开）

| 实验口径 | Agent数量 | 指标 | 原始来源 |
|---|---:|---:|---|
| 5个高难ProgramBench任务平均 | 1 | 19.31% | 微软README |
| 同5项平均 | 128 | 28.78% | 微软README；相对提升约49% |
| Pandoc单项、6小时、同一模型配置 | 1 | 33.89% | 微软README |
| Pandoc单项、6小时、同一模型配置 | 128 | 50.94% | 微软README |
| Pandoc单项、6小时、同一模型配置 | 1024 | **55.06%** | 微软README |
| README另列的新模型Pandoc对照 | 1→32 | 56.19%→79.59% | 模型版本不同，不能和上行混成同一对照 |

**读数方法**：Pandoc从128到1024个Agent，数量增为8倍，最终测试通过率由50.94%到55.06%，是**增加4.12个百分点**；这并非“55%是在100个子任务中完成了55项”，也不是此前5任务均值数据。成本是否划算是另一研究问题，本轮用户明确要求暂不展开规模优化。

### 4.3 第三方“测试基准”与第三方“独立复验”不能混为一谈

**[M-官方]** ProgramBench属于外部公开基准项目，其测试框架与任务不由本轮Agent团队随意在交付时重新设计。微软开源复现指南明确指出使用固定版本的facebookresearch/ProgramBench，并通过自身的评分脚本调用ProgramBench工具，对新克隆、重新构建的提交工件执行评价。

**[D-澄清]** 这属于“采用外部基准、由微软研究团队实施实验/评分”。在没有另一机构按同样配置跑出可验证结果之前，不能称“已有独立第三方完成全面复现认证”。本轮没有审计第三方的隐藏测试全部内容，也没有重复执行这一千Agent实验。

### 4.4 “七七八八做出来了”应如何描述

从工程证明力度说，实验说明团队在限制条件下能够自主组织并交付**具备部分正确功能**的可构建程序，支持“协作流程能产生复杂代码”的判断。它没有证明系统达到产品级可靠性、完整功能覆盖、生产部署、安全合规或可维护性门槛。对我们的项目应使用“可运行原型+客观测试覆盖率”而非笼统的“已经完成七七八八”。

## 5. ACK、CLAIM、共享教训和长期任务：具体如何理解

### 5.1 CLAIM不是原子排他锁

**[M-官方]** CLAIM是公开宣布“我正在处理这个领域”，帮助同伴避让冲突；若发生碰撞，鼓励直接消息协商。**[P-项目]** 对Agensh-Lite来说，多个定时Agent可同时看到READY，也可能同时写入CLAIM；Git会保存两项声明，却不保证只有一名合法执行者。正式共享写入若要求排他，应另有可信Controller事务、grant与fencing epoch。没有通过并发验收时只能标SOFT_CLAIM。

### 5.2 ACK至少有“收到”“处理”“业务接受”三个层次

Agent B的收件箱能够看到新事件，代表消息已经持久化且可见；B写SEEN说明读取；PROCESSED_ACK表示处理；代码审核APPROVED和业务ACCEPTED还须走相应质量门禁。**收到消息不等于已经处理，处理不等于结果正确**。因此我们建议Git事件/目标INBOX/消费游标/ACK及幂等键绑定真实事件，避免错峰定时机器人读漏或重复执行。

### 5.3 共享事实和失败经验必须短、可追溯、可推翻

**[M-官方]** 微软Board定义OBSERVED、FACT、FAIL、CLAIM、PATCH_SUMMARY等短消息，并允许按需展开详情，避免人人重读全部历史。**[R-建议]** 我们将其进一步细化为：事实声明、关联代码/测试/日志证据、适用范围、提出者、版本、反例、状态（有效/争议/撤销）。FAIL优先阻止重复试错，但“曾失败”不应被永久提升为“在所有环境下绝对不可能”，否则会把经验转成污染源。

### 5.4 长时无进度不自动等于死机

一项工作持续一两个小时尚未完成，可能是合理计算、外部等待、模型配额、循环空转、进程失联、网络断开或任务不可拆。需要同时看最近心跳、最近实际输出、日志错误、外部资源占用、到期时间、任务允许的时长。超过租约后旧Agent的迟到输出可留存但不能覆盖新授权版本；接管前要检查未知副作用。此机制是**我们的增强治理建议**，不是微软已经给每项CLAIM配了强租约的证据。

## 6. 微软事件驱动 vs 我们“每小时唤醒+Git恢复”路线

### 6.1 两者运行形态并不相同

| 维度 | 微软Agensh公开实验 | 本项目Agensh-Lite定时工厂 |
|---|---|---|
| 驱动方式 | 工作期间事件驱动，消息/Board可进入正在进行的回合 | ChatGPT等按平台计划时间唤醒，醒来主动查Git；实时能力不能假设存在 |
| 个体上下文 | ACP工作会话与事件延续 | 尽量短上下文；每轮从Git重建权威工作状态 |
| 共享事实 | Gitea + Mattermost + Shared Context Board | Git任务/事件/哈希/回执为持久事实；BOARD是可重建投影 |
| 新任务产生 | Agent可自主发现并开issue | 可研究自治提案，但正式任务准入与权限需符合政策 |
| 冲突协商 | CLAIM + DM + Git合并复验 | SOFT_CLAIM（L0）或独立原子GRANT+fencing（L1） |
| 验收 | 参考行为对比、最终ProgramBench评分 | 分层测试Runner、独立Review、集成与产品评测 |
| 经验共享 | FACT/FAIL等短上下文与详情 | 版本化FACT/FAIL/LESSON + Git证据、热温冷加载 |

### 6.2 用户提出的“上下文错配”应该如何转为研究目标

**[D-讨论]** 用户明确主张**不追求保存每个定时Agent的私有对话长历史**；共同事实必须通过统一Git看板及其事件源及时同步。这个方向降低对不可靠会话连续性的依赖，但引入新挑战：Git内容延迟、异步消息遗漏、重复领取、错误旧状态、旧审查迟到和模型对同一事件理解不一致。

**[R-建议]** 真正需要验证的是“冷启动Agent在无历史聊天的情况下能否恢复到足够正确的业务状态”，而不是让它看起来记住了以前说过的话。每次启动读取：有效POLICY、HEAD、CURRENT/BOARD、自身INBOX/ACK、未完成TASK、HANDOFF、相关证据及当前授权。验证每个状态与真实SHA匹配。Git无法读取时标BOARD_UNKNOWN，不把网络问题理解为“没有工单”。

### 6.3 一组值得长期观测的指标

建议记录事件可见时延、收件处理时延P95、跨Agent因果链成功率、重复副作用次数、CLAIM冲突数、迟到审核拒绝率、断网后恢复耗时、冷启动正确接续率。所谓“上下文恢复真度”可操作化为：在随机抽取的历史断点，Agent是否能正确识别当前权威任务、已有未决Finding、准许动作和禁止动作；不能靠主观自述评分。

## 7. “局部演化”与“系统级RSI”必须分开

### 7.1 局部团队协作调整

例如Agent发现两人修改同一文件会冲突，于是主动CLAIM分区、DM协商、一个人整合代码、另一人针对失败用例补测试。这是现有协作框架允许的任务级自治，发生在权限边界内；改变的是具体协作策略而非全部工厂治理法则。

### 7.2 系统级流程自我改进

例如“所有任务可绕过独立QA”“新的Agent可以任意改变主任务”“全局评分改成自我满意度”“租约授予由少数Agent私聊决定”涉及权限、总评测规则、核心状态机或成本边界。微软官方证据**不足以证明**普通Agent拥有任意实时更改全局系统契约的权限；我们不能因为观察到局部分工便宣称已有成熟的系统级自我递归改进。

### 7.3 用户提出的影子赛道思想

**[D-讨论]** 系统级改进可在旁路并行验证，新版本通过可重复测试后才晋升生产；无需先按原样复制全套50个Agent工厂。

**[R-建议]** 逐级做四种低成本验证：
1. **静态审查**：对新规则做权限、冲突、依赖和失败模式分析，生成可执行反例。
2. **历史回放**：用既有事件日志重算新旧策略决策差异；注意历史日志对新策略的反事实结果可能不完整，不能把“模拟没问题”当真实业务通过。
3. **影子运行**：生产路线保持旧规则，新规则只对同一输入产生候选决策，不获得生产写权。
4. **隔离小流量/沙箱实跑**：选代表性任务与注入故障比较新旧，再提交升级提案；高风险发布仍由指定门禁授权。

评测指标应包含业务成功率、重复/漏单、P95等待、返工率、成本和不可恶化的安全门槛。提案者不得单方改变保留测试集或当前权威评分标准。这是一个**可选RSI研究路径**，目前未部署。

## 8. 从Pandoc黑盒复现转向复杂Web游戏：根本差异

### 8.1 微软的目标比较清晰

其要复现一个已存在程序的可观察行为；统一参考程序就是重要的外部判定依据。参考输入输出、重新构建与自动评分能够提供相对客观的正确性目标。即便如此，55.06%也只是在测定测试覆盖下的通过率，不代表所有隐含场景都已覆盖。

### 8.2 游戏目标不是一条“通过率”可以概括

我们的项目可能同时包含需求/策划、核心玩法与经济系统、科学或故事规则、UX流程、视觉UI、前端交互、后端服务、数据与账号、网络和集成、安全、性能、可玩性。很多模块可以机器验证，但“好不好玩”“审美与沉浸感”“玩法公平与长期留存”需要更丰富的证据与主观体验校准。

**[D-讨论]** 用户的关键洞察是：这些不确定性不是自治系统的停止条件，而是可以让Agent自行研究、辩论、拆解、提问、设计实验的任务本身。包括“哪些指标有意义、谁有权修改指标、怎样验证体验”也可以成为自组织的工作包。

### 8.3 四个一级工作域是候选，而非必须固定为四个互不往来的机器人

可以把完整Web游戏最初提出为四大候选领域：

| 一级候选 | 主要研究/交付对象 | 不能独立决定的跨域契约 |
|---|---|---|
| UX/玩法与产品定义 | 用户目标、游戏循环、规则、信息架构、关键旅程、可玩性假设 | 玩法事件、数据对象、性能预算、可测试性 |
| UI/视觉交互 | 视觉语言、界面组件、状态设计、交互反馈、可访问性 | Design Tokens、组件状态、资源规格和交互API |
| 前端/客户端 | 页面/场景、状态管理、渲染、输入、客户端测试 | API Schema、事件时序、认证、错误态 |
| 后端/数据/服务 | 领域模型、业务规则、服务接口、存储、权限、性能 | 领域事件协议、兼容性、迁移、SLA |

**[R-建议]** 一级规划本身也可以是“规划Agent们的共同任务”：他们可以决定四域是否需要调整为五域/六域，研究切分是否按能力域、用户旅程、垂直切片或依赖DAG更优。不要把用户提出的四块预先当成不可更改的架构真理。

### 8.4 不可忽视的横向工作：接口/集成/质量/体验

如果只让四组各做各的，可能发生UI和客户端状态不一致、前端调用不存在的API、后端数据模型缺字段、玩法规则跨端不一致等。较稳妥的做法是在自治任务池中显式允许产生**横向工单**：接口契约、跨模块集成、测试夹具、部署、观察性、体验实验以及更高层架构仲裁。它们不是必须由永远固定的第五个Agent承担，但必须有可识别的最终责任和验收凭据。

## 9. 进一步推进用户设想：把“规划、评测、评测方法”本身也交给Agent

### 9.1 三层可讨论的自治环路

**第一层：产品研发生态。** Agent提出游戏目标分解、架构备选、模块实现、对接接口和自检方案；新缺口自动生成候选子任务，经过去重、依赖核对和权限准入后进入READY。

**第二层：评价研发的独立生态。** 不参与该候选实现的Agent设计单元/集成/场景/对抗测试、边界反例、体验代理指标，审查开发者自测的可信度；指标可以动态发现，但正式验收基线必须有版本。

**第三层：评价“评价机制”的方法研究。** Agent检查原评分是否过度偏爱容易测的功能、是否遗漏安全风险、是否导致为分而做、是否与真实用户体验相悖；提出新评分法、留出反例、设计对照实验，形成变更建议。

这一架构的关键不是把社会角色固定为永久的“开发组 vs 裁判组”，而是让**提议权广泛分布、最终有效变更遵守共同契约和独立证据**。不同Agent可以轮岗，但同一候选的开发者不应成为无需复验的唯一验收者。

### 9.2 “统一标准”应是框架与证据格式统一，而非所有指标同一数值

所有任务的共同评价协议可以规定：明确目标、可验证输出、测试环境、原始执行结果、证据引用、版本SHA、未覆盖边界、反例、准入/驳回决定。具体指标则按领域不同：后端数据一致性、前端操作路径、视觉规范一致性、API合约、玩法平衡、用户满意等，不必强迫共享一个百分比。

### 9.3 指标演化防止“裁判与运动员同一个人”

研究Agent可提出新指标；独立Reviewer检查定义、遗漏和可被投机利用的空间；隔离Runner使用冻结代码与测试版本执行；新旧标准在一批保留场景上并行，保留分歧及人工/真实用户校准数据；达到约定门槛才有资格版本化晋升。若某标准让通过率提高但体验恶化，应视为指标候选失败或仅部分适用，而非证明游戏进步。

这正是用户提出的**受约束递归自我改进**方向。但“能提出并验证一种更好指标”与“能独立定义游戏价值/替代真实玩家”仍是两件事。

## 10. 评测执行系统：Agent自测、隔离沙箱、第三方平台怎么选

### 10.1 三个正交问题，不是三选一

| 维度 | 核心问题 | 可行主体 | 需要防的风险 |
|---|---|---|---|
| **测试设计者** | 谁提出用例、期望结果与覆盖标准？ | 开发Agent、独立测试Agent、人类、已有基准 | 作者只设计能通过的测试、指标偏置 |
| **测试执行者/环境** | 谁真实安装、启动、操作和运行测试？ | 本机隔离进程、Docker、GitHub Actions/其他CI Runner、第三方SaaS | 环境不可复现、共享生产状态、伪造PASS文字 |
| **验收裁决者** | 谁判定证据符合冻结标准、允许晋升？ | 版本化门禁+不同Agent评审，必要时人类或外部机构 | 旧SHA获批新代码、自我批准、对指标作弊 |

**[R-建议]** 本阶段建议以Agent自动设计测试、独立CI/沙箱机器执行、证据绑定提交与测试环境、独立Agent解释语义缺口为默认组合。GitHub Actions提供一次性Runner执行Python/Node测试和浏览器自动化；Playwright/Cypress等可以验证页面路径；测试命令和真实exit code由Runner而不是Agent文字声明提供。

### 10.2 哪些测试适合纯确定性自动化

- **单元/属性测试**：函数、规则、边界、状态机、定价/数值演算、随机种子下的确定性输出。
- **合约测试**：前后端OpenAPI/JSON Schema、事件字段和兼容性校验。
- **集成/E2E**：测试数据库、API、浏览器、场景状态和跨模块流程。
- **稳定性/安全/性能**：依赖扫描、权限边界、竞态、故障注入、负载与重启。
- **版本与证据**：源码SHA、测试运行ID、日志、退出码、环境镜像/依赖锁定、完整回读。

这些无需每一道题再调用高价大模型“主观判题”。可重现的机械性质优先使用机械裁决。

### 10.3 哪些测试需要AI判断或现实反馈

需求解释、视觉一致性、可访问性体验、玩法趣味性、难度曲线、叙事节奏、美术风格等不总存在唯一真值。可由多Agent比较、视觉回归、模拟玩家/批判Agent产生候选意见，但最终可玩性判断至少应在某个阶段引入真实用户、观察行为或明确的产品负责人取舍。对高风险或主观项目，不能把“多模型一致同意”当成独立现实验证。

### 10.4 不必复制整个生产线：评测沙箱的最小单位

**[R-建议]** 根据变更范围分层隔离：
1. 规则变更：只在历史事件副本与纯函数判定器上回放，零生产写权。
2. 单模块代码：沙箱只启动相关模块+测试替身依赖。
3. 跨模块合同：启动最小前后端/数据库组合与代表性端到端用例。
4. 完整可玩体验：需要真实游戏可部署版本、浏览器/客户端、测试账号、种子数据和体验采集，仍可以小规模部署，不等于复制完整Agent工厂。

沙箱是**隔离执行环境**，第三方测试平台只是潜在执行/能力提供方。第三方基准可增加标准独立性，但并不保证测试覆盖真实需求；内部CI如果规则冻结、身份隔离、结果可复现，同样能提供高质量工程证据。

## 11. 将讨论变成可验证研究：小规模对照实验建议（未授权执行）

**实验A：自主拆解是否真的有效。** 使用相同的Web游戏目标、相同模型与预算，比较“人类预拆固定任务”“Agent自行拆解并自由认领”“Agent自行提出一级规划但接口基线经独立审核”。对比交付可测功能、冲突、遗漏、依赖返工和验收质量，而不仅是工单数。

**实验B：集成角色是否会自然产生。** 比较基础Prompt明确要求人人会合并与减少集成提示后的行为，记录谁实际处理PR、接口冲突、回归、合并，不把声称自己是集成者算实际完成。

**实验C：无历史上下文下的恢复正确率。** 随机中断若干定时会话，启动新Agent只给Git注册表入口，检测是否正确找回未决工单、旧Finding、权威SHA及下轮行动；另测消息晚到两轮、Git读失败、ACK丢失。

**实验D：Agent共同制定评测标准。** 一组Agent提出游戏体验与技术评测标准，另一组找漏洞与反例，冻结基准后由独立Runner对相同游戏候选版本评分；比较与保留场景、真实用户反馈的一致性，记录分歧。

**实验E：RSI影子更新。** 让旁路Agent研究“优先返工还是优先新任务”等策略，对历史账本回放和影子判定，不给予正式生产授租/合并权。检验新策略能否减少重复工作与等待，而不增加越权和漏单。测试通过才提交变更提案，不自动晋升。

**实验F：沙箱类型对比。** 同一个候选commit分别经开发者自测、隔离CI Runner与外部基准/独立审核测试，比较缺陷发现与执行成本。重点证明第三方平台是否真正贡献了增量，而不是假设“外部一定更权威”。

建议先选**一个小型Web垂直闭环**，如“玩家进入场景→触发行动→后端结算→前端反馈→错误恢复”，而不是直接把完整游戏交给几十个Agent全量开发。这个建议不意味着冻结产品方案，只是降低方法验证的混杂因素。

## 12. 与现有Agensh-Lite V4.2保持一致的工程底座

### 12.1 Git事实源，BOARD只是视图

**[P-项目]** Git中任务原件、事件、提交SHA、测试证据、回执共同构成持久事实；BOARD.md/CURRENT.json是由受控写者构建的索引投影。不要把某个Agent的聊天总结、单篇超长Markdown或自身CLAIM视为不可质疑的权威状态。

### 12.2 权威状态与AI认知分工

Mini Controller/Watchdog主要验证：身份、角色、路径白名单、状态迁移、依赖DAG、事件幂等、版本、租约、回执和超时。AI Agent负责：需求、方案、测试设计、语义审查、编码、体验研究；真实Runner负责执行测试并留日志。确定性控制器不依赖“看见PASS三个字”做代码裁判。

### 12.3 级别与阶段

Lite-M纯Git软CLAIM适合安全的初始自治研究；Lite-M+为严格授权/事件处理加轻量Controller；Lite-P复杂动态Agent池不构成首轮上线前提。是否用GitHub Actions处理Watchdog，须以漏触发和强授租并发测试为准；Actions不等于常驻Bridge服务。风险分级独立QA属于我们增加的治理，不是微软每个PR强制经过他人审批。

### 12.4 历史教训对本研究的约束

既有P0/P1实验多次证明：原生ChatGPT定时写入和Work搬运可能受权限、平台安全、文档格式或时序影响；计划触发不等于真实落库；Drive/Git两端要独立回读；旧审查不能批准新SHA；异常写入先查再补；同名文件不能作为唯一身份；Work Relay不能替代开发者产出。研究实验必须保留独立结果、不可变工单和回读证据，防止“多Agent热闹讨论”被误计为实质交付。

## 14. 本轮讨论形成的认识、尚未冻结的选择及下一步

### 14.1 可以视为较稳固的讨论认识

- 把“如何拆解任务”从人工先验工单，升级为Agent可研究、可协商、可验证的对象。
- 微软官方的自组织**有明确公共任务、工具和工作循环边界**；不能误写成无限权限、无限子任务或无测试标准的自由漫游。
- 1024个Agent合作交出一个Pandoc复现程序，55.06%是**该程序的自动评测通过率**，不代表子任务完成率或工业可靠性。
- 复杂Web游戏可先假设多工作域，但任务结构、跨域契约、集成和测试本身都可以进入自治讨论。
- 评测标准可由Agent提出和批评；评测执行应以隔离、可复现的真实Runner证据为基础；第三方专业平台是选择而非前提。
- RSI应分清“局部协作优化”和“系统级规则晋升”；后者不能越过影子实验与正式授权。

### 14.2 仍需用户后续决定的开放选择

本轮没有要求立刻冻结：究竟采用纯自主WBS、混合WBS还是人类先冻结一级架构；游戏体验指标由什么用户样本校准；评测标准提案谁能正式签发；是否为关键流程部署常驻原子授租服务；GitHub Actions、GCP或其他隔离Runner的具体成本路线。以上均保留为研究工单候选，**不自动修改正在运行的任务、配置、仓库主分支或现有QA政策**。

### 14.3 下一次讨论最值得优先追问的问题

**建议优先聚焦“自主规划与自主评测的边界如何设计”这一对偶问题：Agent可以提出任何新任务和任何新测试，但哪些决定必须冻结为项目契约、冻结到什么程度、由什么证据解除冻结？** 这比先把Agent数量扩到几十、几百更能决定无人软件工厂长期自治的质量上限。
