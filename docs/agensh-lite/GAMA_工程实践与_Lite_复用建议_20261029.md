# GAMA 多 Agent 工程实践：对 Agensh-Lite 的可复用经验与实施路线

> 技术交流稿｜2026-10-29｜仅讨论通用方案、方法、实践成果及边界。不包含原项目的仓库位置、文件结构、人员/机器身份、内部任务编号、PR、提交哈希、日志和凭据。本文不是在目标仓库部署 GAMA 的声明。

## 一、核心结论

多 Agent 软件开发不需要首先建设一个庞大的中央编排平台。实践中更有效的最小组合是：**持久化共同事实 + 角色自治执行 + 版本化交付 + 独立验证 + 风险分级集成 + 跨轮恢复**。让 AI 负责问题判断、方案探索和编码，让版本控制与确定性程序负责一致性、并发、防重复和证据。

我们已在一个真实的交互式软件开发项目中跑通过多角色协作、功能交付、缺陷复现、返工、独立验证和最终集成流程；其中的部分操作具有远端版本记录及可复核测试证据。这说明其工程闭环具有实践基础，但不等于通用平台已完成长期无人值守、不同环境的规模化验收。

## 二、已验证有用的设计方法

### 1. 将协作控制面与软件开发面分离

任务状态、负责人、依赖、验收条件与结果证据属于控制面；源码、测试、设计、最终产品属于开发面。AI 可以自主构思实现，但对正式任务状态和代码集成的修改必须遵守不同的权限与验证规则。小粒度状态记录有利于并发修改时将冲突局限在单个任务。

### 2. 不需要长期在线的中央 Manager

Manager 可以是按周期醒来的协调角色：定义目标、拆分任务、处理跨任务依赖、审核集成与异常，运行后保存事实，下轮重新恢复。普通开发、研究和验证工作不要求 Manager 始终在线，但完成状态与高风险变更应有明晰的授权边界。

实践中我们先采用了明确指派的任务流，这更便于控制。下一阶段建议将 Manager 进一步转型为目标治理者和异常协调者，同时让其他 Agent 在低风险范围内自由提出任务与软 Claim。应保留任务去重和冲突协商，避免自治被误写成不受约束的并发写入。

### 3. Git 原生功能优先，避免重复造轮子

通用实现可以充分利用 GitHub Issues、PR、版本引用、Review、Checks、Actions：任务用可机器读取的状态记录维护，代码或文档使用隔离分支交付，独立验证绑定准确版本，最终由可解释的门禁合并。条件写入（基于当前文件版本的乐观并发控制）可避免沉默覆盖；合并前绑定目标提交版本，可以降低审查通过后内容漂移的风险。

这类能力不是数据库意义上的跨对象事务：当提交成功、状态回写失败时，执行者应在下轮先回读真实版本，再进行补偿更新，禁止直接重放不确定副作用。

### 4. Agent 的角色可区分，能力不应被提示词夸大

最小角色包括：目标/集成协调、设计研究、编码执行、非作者验证。云端 Agent 可以研究、静态审查和交付代码，但没有真实运行环境就不能声称浏览器或本地测试通过。需要可执行验证时，由有真实运行环境的执行端检出**精确交付版本**运行测试，记录命令、环境、退出码和结果。版本变化后旧验证不得直接沿用。

### 5. 定时唤醒是运行机会，不是业务有效期

周期调度用于发现未完成工作和增量变化。早醒、晚醒或某轮没有新任务，不构成终止条件；任务跨轮保存检查点。每次执行应先对账远端任务与交付事实，再决定领取、继续、返工、等待或局部阻塞。调度系统无须重复实现任务状态机。

### 6. 对失败采取局部恢复而不是全局停机

实际协作出现过：作者自测和独立测试结论不同、测试假设错误、代码变更导致旧验证失效、交付产物与源码不一致等情况。有效办法不是宣布整个工厂失败，而是保留最小可复现证据、只阻断受影响集成动作、明确返工条件、修复后重新独立验证。必要时先证明旧版本失败、再证明新版本通过，比单纯报告“测试通过”更可信。

## 三、工程实践取得的成果（匿名化）

一个完整项目经历了需求拆解、并行设计与开发、可运行功能交付、独立测试、质量升级以及真实缺陷返工。代表性成果包括：

- 完成可运行的交互式产品，具备输入、状态切换、用户界面与基础持久化行为，并持续开展功能升级。
- 开发者产物和独立验证的版本相互绑定；对游戏逻辑执行自动化测试，对关键交互使用真实浏览器自动化验收，而非只有静态代码审查。
- 一次关键逻辑缺陷通过旧版本可重复失败的反例定位，修复后新增回归测试并进入正式集成。
- 一次界面缺陷经历多轮失败、返工及对更新版本重新验证；测试结果未被简单覆盖成成功。
- 使用状态条件更新、版本回读和风险分级验收，减少重复交付、误报完成和未经验证的集成。

**证据边界**：这些是对已发生实践的匿名总结，不提供源仓库或私有运行日志；不声称在此公共仓库重现了相同案例，也不声称实现了完整的可靠消息总线或 7×24 小时稳定运行。

## 四、与 Agensh-Lite V1.3 的互补关系

| 能力 | 工程实践可复用的方法 | Lite 下一步建议 |
|---|---|---|
| 工作空间与版本集成 | Git 事实、独立交付、版本绑定、PR 检查 | 直接采用原生 GitHub 能力，避免另建代码协作中心 |
| Manager | 周期协调、任务拆解、异常与集成处理 | 从微观派工逐步转为目标治理，不应强制所有 Agent 经中央派单 |
| 任务状态与并发 | 独立状态对象、条件写入、远端回读 | 保留小型确定性守卫，不必一开始上独立数据库 |
| 可靠执行 | 跨轮检查点、先对账再行动、局部失败恢复 | 增加事件身份、收件人 ACK、去重、Gap 补扫的最小实测 |
| 质量门禁 | 非作者验证、精确版本、自测与集成检查 | 按风险分级，不把探索笔记强行套用代码合并门禁 |
| 自主协作 | 已有角色分工、依赖检查与协商经验 | 增加软 Claim、Agent 自主发现缺陷与请求支援 |
| 定时触发 | 周期唤醒、状态持久化、错峰 | 调度与业务生命周期解耦，接受迟到、漏轮和下轮恢复 |

## 五、推荐最小演进路线

**第一阶段：以现成平台完成最小闭环。** 一个共同目标、一组可追溯任务、两个执行角色及一个独立验证角色即可。复用 Issues/PR/Checks/Actions 或等价原生工具。验证从需求到运行产物的全流程，并真实记录失败与返工。

**第二阶段：引入低风险自主 Claim。** 允许 Agent 依据共同目标提出细分任务、发现 Bug、报告风险、自主认领不冲突的工作。Claim 默认是协作声明而非硬锁；冲突时协商，正式写权限仍由平台约束。验证 Manager 暂时缺席时是否可以继续产生有价值的增量。

**第三阶段：用最少机制实现可靠异步消息。** 事件须有稳定 ID、作者/接收者、关联任务、来源版本和可回读状态。不同接收者独立确认；重复、漏轮和写入结果未知要通过对账处理，绝不盲重试可能造成副作用的操作。先测试两个 Agent 的跨轮消息闭环，不急于引入数据库或常驻路由服务。

**第四阶段：以运行证据决定是否扩容。** 监控任务交付成功率、事件延迟与积压、重复副作用、失败恢复时间、集成缺陷、模型/运行资源成本。只有当 GitHub 原生设施或周期调度确实成为瓶颈，才考虑专用事件服务、数据库或其他基础设施。

## 六、应刻意避免的复杂度

不要为了“自治”再建一个代替 GitHub 的中央任务系统；不要因普通任务超时、回执字数或 Claim 重叠而全局停机；不要每轮读取全部长篇规范；不要把模型说的 PASS 当作可执行测试证据；不要将提示词约束当作真正的平台权限；不要复活已被更简单直接协作模式替代的中转同步层。

## 七、最终建议

优先构建一个**轻管理、强事实、可恢复、可验证**的最小自治软件工厂：人负责目标和不可逆风险，Agent 自主发现与完成工作，Git 平台提供协作事实，少量确定性工具守住消息、并发及交付正确性。Agensh-Lite 的 Gather → Claim → Act → Verify → Publish 循环非常适合作为认知协作层；现成版本控制与测试机制适合作为工程可信层。两者结合比单独扩张某个中央 Manager 或重写一整套基础设施更稳健。
