# 第一卷｜Agensh-Lite 自组织软件工厂：总体架构与原则 V1.3 正式版

> **一句话**：尽量照搬微软 Agensh 已证明的 **Gather → Claim → Act → Verify → Merge** 自组织循环，把它用 Git 共享工作区、Markdown/JSON 异步消息和少量 Python 确定性工具实现；ChatGPT/WorkBuddy 的原生定时唤醒只是不同的事件消费时机。**宽容节拍、严格事实，不做中央指挥系统。**
>
> **效力**：经用户批准，V1.3 作为当前正式**设计纲领**取代 V1.2.1 三卷正文；V1.2.1 七类结构化机器合同继续兼容适用。此发布**不等于运行部署验收**，也不授权创建/修改定时任务、合并 PR、推 Git、部署 GCP 或改变权限。未获批准的路径、身份、参数仍为 `UNDECIDED`。

## 1. 首先向微软复刻什么，不复刻什么

**优先复刻的协作精髓**（论文 §2.1–§2.3、附录 A/B；代码 `prompts/agents.txt`、`board-service`、`mini-router`）：

1. **Agent 平等自主**：围绕共同目标自己发现缺口、提出子任务、公开 CLAIM、实施与验证；无需中央 Agent 分配全部任务。角色可以临时形成、协商更换。
2. **独立开发、共享进展**：个人分支/独立工件自主写入；整合采用 Git 版本控制、PR、冲突处理，代码发布后其他人看得到。
3. **短事实和失败经验共享**：`FACT / OBSERVED / FAIL / CLAIM / PATCH_SUMMARY` 短信息优先，详情只在需要时搜索与展开。
4. **消息驱动的协作**：公告、请求、冲突、答复和交付都成为持久事件；不同 Agent 可以异步读取和响应。
5. **可靠投递**：消息有身份、去重、待处理状态、失败重试和重启补收；传输可靠性由轻量程序承担，不依赖 AI 猜测。
6. **真实可验证成果**：自测、集成和合并是循环中的基本动作；反例可能推翻已有认同，合并受当前工作树和真实证据约束。

**暂不复刻的重型载体**：Gitea+Mattermost+MySQL+持续 ACP sidecar 的整套常驻集群、1024 Agent 部署、实时插入工具返回的中途消息机制。它们是微软原版的实现，不是其组织原则的唯一实现。以后是否引入，取决于运行瓶颈的实证和用户另行批准。

**我们特有、要标清身份的适配**：Git Markdown/JSON 消息承载 Mattermost/Shared Context 的部分功能；平台定时唤醒代替即时通知；冷启动从 Git 交接记录恢复；ChatGPT 可见回执保持简短。这些是 **[ADAPT]**，不得声称是微软原生实现。

## 2. 系统只有三个协作面，加一个很薄的机械保障

| 面 | 微软原版 | 我们的轻量承载 | 权威边界 |
|---|---|---|---|
| Shared Workspace | Gitea + 私人 checkout/branch + PR | Git 仓库的代码、任务、独立工件、PR | 已确认提交、版本和合法合并为准 |
| Message Interface | Mattermost 频道/私信 | Git 中定向消息、公告、请求与各收件人 ACK | 消息已写入≠对方已处理 |
| Shared Context | append-only board + short gist / grep / unfold | 简短 Markdown/JSON 事实、历史检索、详情指针 | 短摘要不是对原始证据的替代 |
| Transport/Recovery | mini-router + MySQL 状态与游标 | 小型 Python 检索、去重、补扫、回执、冲突检查 | 只管机械可靠性，不管语义优劣 |

不新增“中央总指挥”。Python 不负责挑选玩法、拆整个 WBS、决定哪位 Agent 最聪明、审判创意或硬性安排所有工作步骤。任何所谓自动分派必须是 **可以解释的读取/路由辅助**，而不是取代自组织。

## 3. 核心工作循环：以目的组织，而非以步骤数卡死

`Gather（目标、本人未完工作、近期事实和新消息） → Claim（提出或接手有用工作，必要时与他人协调） → Act（编码、探索、设计、试验） → Verify（用适当证据检查） → Merge/Publish（把成果或失败经验对外发布） → 下一轮`

五步是**循环原则，不是每次定时唤醒必须在同一轮完成五步**：一轮可以只完成研究、发现新的失败，或等待测试完成；持续有进展或说明合理阻断即可。微软的工作循环没有要求每次唤醒完整执行固定 12 个门禁动作。

- **Claim 是协作宣示**，不是天然排他的网络锁。与其他 Claim 重叠时主动沟通、分工或保留两份探索，不因此冻结整个项目。
- **Verify 的严格度与工作性质匹配**：创意探索可以用观察、原型与反例；代码必须有适当测试；受保护代码/正式发布必须有真实版本与授权依据。微软原版没有“所有 PR 必须经过两个人审批”的硬规则。
- **Merge/Publish 不同于聊天回答**：代码经版本化整合；发现/失败通过简短事件共享；未真正合并不得自称已合并。

## 4. 事件触发与定时触发的共同语义

事件是“发生了什么”，触发器是“什么时候查看”。两者可复用同一个消息、Claim、确认与恢复协议。

- 微软：事件进入持久队列，尽快通知匹配 Agent；部分私信和共享事实能在工具返回边界中途送达。
- Lite：ChatGPT/WorkBuddy 在平台允许的间隔醒来，拉取上轮以来的新事件；事件在轮次之间持久保存，执行中暂未收到的消息由后续轮次处理。
- **调度时刻是期望，不是工作资格**。早到、晚到、错峰、漏一轮，不得单凭时差判任务失效；优先处理仍然有效的未完工作。真正的用户明确截止、不可逆成本和被撤销授权仍有效。

**必须避免**：让“计划 10:10、实际 10:13”自动变成 `MISSED → ABORT`；让“早醒三分钟未看到新消息”自动关停后续轮询；为了提交一个简短摘要反复计算 500 字的精确阈值。这些不属于微软协作循环所要求的安全性。

## 5. 规则优先级：仅给不能越过的边界设硬门禁

| 级别 | 性质 | 示例 | 违反时的动作 |
|---|---|---|---|
| **HARD** | 授权/不可逆风险/真实证据 | 平台拒绝、无授权写受保护分支、明确硬性停止生产时间、付费越界、秘密泄露、把未测试冒充通过、对未知写入盲重试 | **阻断受影响的动作**，保留候选和证据；不连坐整个工厂 |
| **SOFT** | 操作偏好/效率目标 | 错峰时刻、正常回执建议短、一次优先处理一个任务、推荐写入宽限、建议摘要长度、建议重试间隔 | 记录偏差，尽量继续；允许合理延迟和下轮接棒 |
| **ADVISORY** | 参考经验/默认建议 | 角色划分、代码目录结构、首次 Agent 数量、报告风格、上下文建议容量 | 按环境调整，无需发起停机流程 |

**判定方法**：某条件若只是为了让报表整齐、时间对齐、文本长度统一，而违背它不会引起安全、成本、事实、交付损失，就不应写成强制停止。严禁 AI 自行增加“晚于计划 X 分钟就放弃”“超过建议字数就不交付”等限制。

**显式终止条件例外**：如果用户给出的是真正的**生产禁写截止**或法律/付费授权期限，必须守住这个权限边界；但可只读检查、保留草稿或在重新授权后续跑，不能把它理解为所有任务数据失效。

## 6. 保留轻量而非再造重型

**首期最小能力**：已有定时任务 + Git 读写 + 角色化独立文件 + 短消息/历史检索 + 简单 Python 事件去重/游标/回放/验收查询 + Git 自身 PR/冲突/版本 + 已有真实 Runner。

**不要首期强制**：中央任务规划器、全局 Context Assembler、独立数据库强租约、大规模动态派工、多个相互竞争的 BOARD Writer、每步审批、复杂在线预算引擎、向量数据库、第二套消息中心。

原 V1.2.1 的七类 JSON Schema、身份与证据格式、评测/集成合同在结构化生产对象中继续作为兼容基线；它们属于我们的治理资产，**不是**微软源码里天然存在的七类状态机。在尚未获批迁移的结构化 TASK/EVENT/MESSAGE/ACK/REVIEW/DELIVERY/RUN 写入中，继续沿用 V1.2.1 已冻结的机器合同；普通研究笔记和展示摘要不需要伪装成七类机器对象。详见第二卷§12。涉及有副作用的跨平台写入时必须保持必要的幂等和回读。

## 7. 三卷使用方式及版本路线

- **第一卷**：唯一的总体原则和路线边界，不塞大段 Schema。
- **第二卷**：Agent 需要做什么、如何可靠发表消息、如何在 Git 协作；提供极简启动模板。
- **第三卷**：分阶段验收与证据边界、故障注入和历史裁剪；只有真实风险才硬阻断。
- **附包**：V1.2.1 七份 Schema 和七份正例作为原样留存，不代表 V1.3 运行时已部署；逐项微软来源对照独立保存，不让定时 Agent 每轮通读。

三卷是**治理母版**，不是定时任务每轮全文输入。微软用 `board_read/grep/unfold` 和增量 Snapshot 实现短事实传播，我们优先继承该思想。普通 Agent 自主扩展检索，不能硬卡总阅读字数，也不能默认扫描所有目录。

## 8. 范围、未决事项和生效条件

- **已决定**：轻量主线；重型复刻冻结；独立写本人产物；共同 Git 事实；事件与定时共用协作语义；软时间/软篇幅不造成停机。
- **仍待选择**：唯一仓库与分支、私有/公开、Python 运行宿主、各 Agent 真实 Git 授权、轮询频率、具体预算、是否需要真正强租约。这些须经 L0 核验，不在本文猜测。
- **现行状态**：**V1.3 正式设计基线已获批准**；原 V1.2.1 三卷归档供追溯，七份结构化机器合同仍保持 `AGL_LITE_V1_2_1`，不得静默迁移任何活跃事件流。本次发布不重启重型 PR，不修改生产任务或凭据。

## 9. 两条执行通道并行，不设中央指挥 [P1-04]

同一项目可同时使用 **A. Git 异步协作** 和 **B. GCP Bridge → WorkBuddy 明确委托**。A 保留微软式 Agent 自主发现/Claim/协商；B 是发起者明确授权的某项任务快速执行，不拥有更高认知或治理权。任何通道都不改变 Git 作为共享任务、消息、成果与审核的事实来源，也不赋予 Bridge 越权推送正式状态或受保护分支的能力。

- **继承微软 [MS]**：自主工作、共享进展、协作消息、短事实，以及事件持久化和可恢复交接。
- **本地适配 [ADAPT]**：定时轮询代替即时事件通知；Git Markdown/JSON 代替部分 Mattermost/Shared Context 承载；GCP Bridge 是新增的*可选执行通道*，不是微软原版组件。
- **绝对不预设 [UNVERIFIED]**：Bridge 支持状态查询、服务端幂等、跨轮执行或定时任务内可达，目前均需独立真实测试。接口能力与提交成功必须分别判定。

两条通道统一遵守“任务身份稳定、执行证据可回读、未完成不冒充完成、写结果未知不盲重试”；**不强制所有普通 Agent 都经过 Bridge**。第二卷§15给出最小契约，第三卷§11给出独立验收。

## 10. 可靠性规则只保护事实与写权限，不绑定轮次整齐度 [P1-01～P1-03]

简洁的五步循环继续是默认工作方式。只有在正式结构化对象、跨收件人 ACK、公共投影及受保护代码集成等存在一致性风险的地方，继承 V1.2.1 原有可执行契约和授权检查。具体对象与生效条件以第二卷§12～§14为准，**它们约束相关写操作，不要求全部 Agent 每轮填写七种 JSON，也不以时间/字数偏差停止系统**。
