# 统一架构总框架
## FactoryOS：支持十大工厂与多种业务管理模式的 AI 生产操作系统（V1.0）

> **统一共识**：FactoryOS 是平台；DeepSeek Harness 是可替换的智能体运行与编排引擎；Agensh-Lite 是自治协作策略；Taskboard 是管理组件；Gateway 是跨端执行连接设施；Git/Markdown 是共享版本、消息、事实与交付证据的核心载体。平台应能严格组织生产，也能放手让 Agent 自组织探索，最终支撑十大工厂业务。
>
> **效力边界**：本卷记录 2026-10-30 已达成的产品及架构方向共识，为平台级上位设计说明。它不修改 Agensh-Lite V1.3 已冻结的第一至第三卷，不静默修改七类 AGL_LITE_V1_2_1 机器契约，也不意味着实际部署、运行验收、生产写入、定时任务变更或 PR 合并已获授权。

## 0. 文档定位、版本关系和核心裁决

过去方案从单 Agent 编程、多 Agent 定时轮询、Git Markdown 接力、WorkBuddy MCP 云桥、Codex/SDK 联动，逐步演进至统一管理平台。这些实验的共同发现是：**可调用的 Agent 越多，连接协议、状态、权限、重试、模型配额、Git 交付与审计越需要系统化管理；但管理的强度不能强迫所有项目都采用中央派工。**

本卷解决的是「平台应支持什么」；Agensh-Lite V1.3 三卷解决「M2 去中心化自治协作应如何运作」。二者既不互斥也不互相覆盖。微软 Agensh 是有价值的自组织参考与实验路径，不是 FactoryOS 的唯一组织范式；DeepSeek Harness 是可选运行底座，不是整个系统唯一的理论依据或不可替代的锁定组件。

**裁决**：平台统一基础设施与治理接口，项目自行选择组织模式；同一项目甚至同一工作流的不同阶段可以混用中央、自治、混合模式。不能把“统一管理”误读为“统一由中央决定每个 Agent 做什么”，也不能把“去中心化”误读为“没有权限、预算、资源或发布管理”。

设计原则的优先级依次为：**真实授权与安全 > 事实正确与可验证交付 > 持续推进与故障隔离 > 项目管理模式适配 > 资源效率与成本**。对单次执行失败、软时刻偏差、软 CLAIM 重叠采取局部处理，不应连带停止整个工厂。

## 1. 平台的业务使命与能力边界

FactoryOS 的产品目标不是单一聊天助手，而是面向多业务域的 AI 生产管理平台：能够把项目目标转化为可观察、可协作、可追责的持续生产过程；既能在中央编排下进行标准化交付，也能让多 Agent 基于共享事实自主发现问题、协商研究、产生反例与交付成果；能让云端、本地和未来新增的执行器通过统一协议被授权调用；能在断线、超时、配额耗尽、代码冲突和执行器更换时保存事实与恢复工作。

平台支持四种用户体验：自然语言交互、统一项目及工厂看板、Git/Markdown 内容资产管理、机器可调用的 MCP/API/SDK。交互入口应可替换，不得把业务真相保存在某一个聊天会话的上下文里。

**能力覆盖不等于已经部署**：架构支持某项能力时标记 DESIGN_SUPPORTED；存在源码或历史试验时标记 IMPLEMENTED_PARTIAL/LOCAL_TESTED；只有当前指定环境的真实读写、独立回读和故障测试完成，才可标记 REMOTE_VERIFIED。任何平台或插件升级不得凭说明文档自动晋级。

## 2. 三种生产组织模式（按项目/阶段选择）

| 模式 | 决策和派工权 | Agent 自主空间 | 典型用途 | 主要验收依据 |
|---|---|---|---|---|
| M1 CENTRAL（中央编排） | 中央工作流/授权运营者制定阶段任务、依赖、资源与里程碑 | 在指定任务内自主执行和优化 | 标准化软件交付、客户项目、批量内容和正式发布 | WBS、任务状态、测试、风险门禁、最终交付 |
| M2 AUTONOMOUS（去中心化自治） | Agent 围绕共享目标自行 Gather/Claim/Act/Verify/Merge，协商分工 | 高；普通 CLAIM 为软声明，可重叠探索 | 微软 Agensh 风格蜂群实验、开放研究、技术探索 | Git 消息、独立 ACK、可复用事实、反例、PR/成果 |
| M3 HYBRID（混合协同） | 中央确定目标/边界/预算/里程碑，Agent 自主发现子任务和协商；集成受控 | 中高；正式发布与外部副作用走门禁 | 创新软件、游戏、复杂产品研究、跨学科研发 | 阶段成果、自治发现、整合测试与正式交付 |

**模式是协作策略，不是三套不同的基础设施。** 所有模式共用身份、工具连接、执行能力登记、事件/证据格式、Git 版本和权限边界。M1 可以强管控工作顺序与资源；M2 不得被中央任务表的 READY 状态挡住所有合法探索；M3 由明确的项目策略说明哪些环节中央控制、哪些环节自治。

同一项目可以在「研究发现 M2 → 原型验证 M3 → 正式交付 M1」之间转换，也可以同时设立不同模式的工作流。转换必须留下策略版本、切换时间、作用范围、在途任务处置与审计记录；不得悄悄取消已领取工作、抹除消息 ACK 或覆盖旧交付。

### 2.1 建议的 Project Policy（示意，非现有机器 Schema）

~~~yaml
project_id: F3-GAME-001
policy_version: 1
default_mode: HYBRID
phases:
  discovery: AUTONOMOUS
  prototype: HYBRID
  release: CENTRAL

  exploration: SOFT
  protected_write: AUTHORIZED_CAS
execution:
  targets: [LOCAL, CLOUD]
  selection: CAPABILITY_COST_DEADLINE

  formal_delivery: READBACK_REQUIRED
~~~

此配置只是管理策略样例，不得与已冻结的七类 AGL_LITE_V1_2_1 TASK/EVENT/MESSAGE/ACK/REVIEW/DELIVERY/RUN 混为一谈。后续如引入机器执行契约，必须另设版本、兼容策略及负例验收；不能静默重写正在使用的旧流。

## 3. 总体技术架构和组件职责

~~~text
            ChatGPT网页/手机  |  Harness Web  |  WorkBuddy  |  Factory Dashboard
                                      |
                        统一身份、项目、策略与可观测视图
                                      |
          +-------------------- FactoryOS 管理平面 --------------------+
          | M1中央工作流 | M2 Agensh自治策略 | M3混合策略             |
          | 项目/工单视图 | 风险审批与预算 | 能力注册与运行审计      |
          +-----------------------------+----------------------------+
                         /                          \
        Git异步协作通路 /                            \ MCP/SDK/API委托通路
                       v                              v
       Git Workspace + Message + Context     Agent Gateway / Adapter Registry
       Git Markdown / JSON / PR / ACK        节点发现/任务投递/状态查询/回收
                       |                              |
                       +-------- 各执行环境 ---------+
                                   |
             零刻本地Buddy/Codex/本地模型 | GCP云端Buddy/CodeBuddy/外部工具

                     版本化产物、证据、回读、审计与对账
~~~

### 3.1 FactoryOS（平台）

负责统一业务域、项目、策略、身份、权限、资源策略、运营视图、任务治理与交付质量的公共约定。平台提供统一视图和接口，不要求所有任务都经过单一 AI 的语义决策。长期架构上控制平面应可独立于具体 Harness 更换或降级。

### 3.2 DeepSeek Harness（可替换运行与编排引擎）

优先复用模型接入、Cordis 插件、Skills、MCP、子 Agent、对话和 Web UI；M1 中可以承担智能任务拆分和编排，M3 中可以组织混合工作流，M2 中仅作为参与的 Agent 运行时或辅助工具，不强制垄断任务发现。平台应以适配器/API 封装 Harness 能力，避免把全部业务规则写进其内部插件私有格式。

DeepSeek Harness 目前属于快速迭代的开发预览软件，正式安装前必须冻结版本并在隔离环境验证插件兼容与安全；不得因存在官方/社区插件就声称生产可用。

### 3.3 Agensh-Lite（M2 自治协作策略）

沿用已批准的 V1.3 第一至第三卷与五步循环：Gather → Claim → Act → Verify → Merge/Publish；共享工作区、定向消息、短事实/失败经验分开；普通 CLAIM 是软协作宣示，不是强占有锁；Agent 通过 Git 各写各的工件、发布共享可见消息、按需协商或交接。明确保留事件驱动和定时轮询两种发现时机，早醒、晚醒、漏醒不能仅因时间偏差使合法任务失效。

七类 V1.2.1 机器合同继续适用于其定义的正式结构化对象；普通研究 Markdown 和共享简短知识不需伪造七种对象。M2 的合法 Git 自治协作**不得依赖 Gateway 或 Harness 在线**。

### 3.4 Taskboard（管理和展示组件）

负责项目/工单可视化、中央任务状态、人工审批、看板检索与异常提示。它的内部存储不是 Git 原始文件的第二份权威。社区 Taskboard 的独占 Claim 可以用于 M1 执行槽或受保护工作，但必须适配 M2 的 SOFT CLAIM，不能默认以独占认领阻断并行研究；若无法正确适配，只作为只读展示或中央模式组件。

### 3.5 Agent Gateway（跨端执行连接设施）

负责经过授权的节点注册、心跳、能力/配额上报、任务传输、实际执行尝试记录、结果查询、取消、超时和孤儿状态对账。它不负责项目认知决策，也不能覆盖 Git 的正式代码或交付事实。ChatGPT 与 Harness 均可在授权范围内直接经 Gateway 调用执行器；任何一个交互入口的不可用不应阻断其他合法通道。

Gateway 首期只实现跨端连接、受控投递和基本状态管理，不新建一个覆盖全项目的重型中央 Controller。必要的持久化、幂等、认证、审计属于网络可靠性，不等于中央 AI 派工。

### 3.6 Git/Markdown/JSON（共享事实与成果载体）

Git 负责工作区、历史版本、不可变事件、独立 Agent 工件、PR/Commit、正式可见消息与交付证据；Markdown 便于人和 Agent 阅读，JSON 用于可靠消息和机器验收。公共 BOARD/索引应从原始事实重建，不能让多个 Agent 直接争写一份不断膨胀的权威看板。Git 可作共享消息载体，但不天然提供实时队列、跨云锁和数据库事务。

### 3.7 执行池（WorkBuddy、Codex、本地模型及专业插件）

执行器只报告经探针验证的能力和可用状态。模型与工具在本地、云端动态选择，允许不同项目使用不同的经济性、隐私和截止期策略；一个节点报告 READY 不代表所有模型配额均可用。执行器不因拥有高权限凭据而自动被授予修改所有工厂正式 Git 分支的权利。

## 4. 双通道协作：默认开放 Git，自选直接委托

**通道 A：Git 自治/异步消息。** Agent 读取共享目标和新消息，发现工作、软 CLAIM、自主执行、验证，在个人分支/消息目录发布事实或成果。任一 Agent 可在合法 Git 权限下直接参与，不必经过中央模型、Gateway 或 Taskboard 认领。

**通道 B：MCP/SDK/API 明确委托。** 用户或编排器指名任务，经 Gateway 调用云端或本地 Buddy/Codex。外部执行产生稳定 task_id、attempt_id、remote_job_id、结果状态与证据。完成的代码/研究产物仍按目标项目要求回写 Git、回读并确认，不把「MCP HTTP 200」「Agent说完成」当业务交付成功。

**融合原则**：两通道统一身份、操作去重、结果证据及正式发布权；不得互相重复认领同一个有副作用的执行任务。Bridge 是否在线只影响其承载的直接委托，不影响可继续的 Git 自治工作；反过来 Git 暂时不可用时，可继续被授权的无 Git 副作用的研究/本地执行，但不能假报正式 Git 交付。

## 5. 云端与本地双端互联策略

现有 GCP WorkBuddy MCP V3.4-candidate 已实际健康检查与短任务调用成功，接口含健康检查、异步提交、结果查询、队列查询、取消；桥接器已具备 FIFO、超时/孤儿任务账本等部分可靠性机制。该节点是**云端执行器及轻量接入网关**，不是零刻本地机器。

第一阶段保留现有 GCP 生产桥接器，不修改其模型、服务、凭据、队列和超时策略；新增跨端组件先隔离开发。零刻本地节点建议通过受控 HTTPS 长轮询或 WebSocket **主动出站**注册和领取任务，避免向公网开放家庭 Shell 或假设 GCP 可直接访问本地 NAT 设备。

主控部署目标为零刻 GTi13 Ultra；GCP 轻量 VM 优先保留作为云端 Buddy 与桥接服务。零刻具体 Node/SDK/端口等尚未经当前远程会话核实，不能把云端 shell 预检当成本地事实。Gateway 的外部入口须验证 TLS、鉴权、节点权限、最小功能、速率限制和审计，不允许裸露任意命令执行。

**双端任务最小语义**：一次项目工单可有多次执行尝试；使用稳定 task_id 和新的 attempt_id 映射实际执行器 job_id；节点离线保留未领取任务，执行中离线进入待核对；已产生未知副作用的尝试不能直接跨节点重投；远端取消需核实终态，客户端超时不能宣称远端已经停止。试验中要证明本地与云端各自真实执行，而非由另一端模拟代答。

## 6. Git Markdown 文件集群管理

正式能力范围：目录索引/搜索、内容编辑、版本差异、认领记录、跨 Agent 冲突协商、提交、PR、回读、交付、重复与缺失对账、审计追溯。可优先复用 dsh-git / DSH Taskboard / Markdown 编辑类插件，但任何第三方插件必须源码审查、隔离安装、固定版本、权限最小化；是否采用一体化界面不改变 Git 的权威。

建议复用 V4.2 WorkBuddy 分支已开发的 Git storage、immutable write、CAS、独立二次回读、SHA 对比、事件日志和 CLI。它们有历史测试记录，但 PR #1/#2 尚未合并，不能冒充生产部署。修改重点是：
1. 正式 ACK 依照原 AGL_LITE_V1_2_1 ACK Schema，而非旧适配器私有简化回执直接混写。
2. 对已证明连续 stream_seq 的流，维护每收件人连续水位；E1/E3 已 ACK、E2 未 ACK 时水位不能跨过 E2。无连续序号的流用稳定 ID 差集和补扫，不用最大时间戳假装连续。
3. 普通软 CLAIM 允许重叠并协商；强锁只用于有限执行槽、受保护代码/公共投影和不可逆外部操作。
4. 工作分支修改→必要测试→PR/合法合并→目标 Commit/Blob 与来源内容独立回读；未合并 PR 不称「已发布生产」。
5. 不可变事件记录与公共 BOARD 投影分离；正式投影单写者或 Git CAS、失败刷新 HEAD 重算，禁止强推覆盖。
6. Git 文件数量相等不代表对账完成，必须结合稳定业务 ID、来源、内容 hash、目标路径、Commit、实际授权和最终验收。

**文档/任务/执行三类状态不得混同**：MESSAGE 的 SEEN/PROCESSED ACK 不是 TASK DONE；Gateway 的执行成功不是 DELIVERY VERIFIED；Git Commit 已存在也不是 PR 已合并。

## 7. 项目策略、权威边界及可解释调度

统一管理面管理项目策略，不替任何项目预设唯一工作法。项目策略至少说明：模式、目标与授权、Agent/工具能力、预算/期限、CLAIM 规则、需加锁的资源、正式 Git 写入及审批规则、交付/审计等级、允许的执行池和模式切换策略。

| 事实/操作 | 权威来源 | 其他组件的角色 |
|---|---|---|
| 代码、Markdown 文件内容与版本 | Git Commit/Blob/PR | 看板索引、全文检索、结果引用 |
| 自治消息、FACT/FAIL、软 CLAIM | 共享可见 Git 消息及原始工件 | Taskboard 映射、Gateway 仅辅助通知 |
| M1 中央任务与流程决策 | 指定工作流/项目策略的受控状态 | Git 记录审计快照和成果指针 |
| 节点心跳、外部执行尝试与队列 | 对应 Gateway/执行器真实回执 | Harness/看板读取与展示 |
| 正式验收/生产发布 | 获授权的验收规则 + 目标证据 | Agent 提供测试/建议，不能虚构完成 |
| 项目模式、授权与预算 | 获批准的版本化 Project Policy | Harness/Taskboard/Agent 按规则运行 |

M1 可以强制派工、执行顺序、资源配额和阶段发布；M2 可以自主开放软认领；M3 组合两者。在任何模式下，授权、保密、受保护写入、不可逆外部副作用和真实证据都有不可越过的边界。除了硬边界，时间偏差、软 CLAIM 重叠、正常摘要篇幅等应视为 SOFT 或 ADVISORY，单项异常局部修复，不导致全厂停机。

## 8. 消息、执行与交付的最小可靠性约束

**身份**：project_id、factory_id、agent_id、task_id、attempt_id、message_id、operation_id、commit_sha 等稳定关联；不同运行时的内部 job_id 保留原貌，不混淆为业务主键。每个授权主体与实际执行器独立标识，不用同一高权凭据冒充多个独立 Agent。

**去重与恢复**：有副作用动作使用稳定 operation_id 和条件写入/回读；ACK 独立到每个收件人；未知提交先只读核对，不能盲目重试；漏醒通过可重放消息、增量检索和有界补扫恢复；并发版本变化后重新验证。不能笼统承诺分布式 exactly once，只能以幂等和可核验证据减少重复副作用。

**状态边界**：传输已受理、远端运行、远端可能残留、测试通过、Git 已写、Git 已回读、正式验收或合并均是不同事实。统一看板显示完整证据链，不能把 HTTP 200、目录存在、短回执或过往日志替代最终交付。

**故障隔离**：模型 429、节点 OFFLINE、超时、Git 409、ACK 丢失、索引延迟、单 Agent 不可用均优先局部告警、有限重试或交接；只阻断风险动作。用户明确截止/预算耗尽、无授权发布、秘密泄露或无法判明的不可逆副作用需要强阻断对应行为。

## 9. 安全与可信运行

1. **最小权限**：本地零刻、GCP 云桥、GitHub、模型 API 分开账户/密钥/作用域；不同 Agent 有真实身份，目录提示词不是 GitHub 的强授权。
2. **隔离第三方 Harness 插件**：官方 Harness 为开发预览，需隔离工作区、容器/沙箱、版本冻结、来源审计与回滚；不能直接授权其访问全部主目录、生产凭据和 Git 主分支。
3. **受保护写入**：有条件提交、实际 HEAD/Commit 校验、PR 与必要审查；真实 GitHub 分支保护及 Ruleset 必须经具权限的检查确认，不以 Prompt 代替。
4. **可追踪委托**：受控任务描述与工具白名单、超时与资源预算、Prompt 注入防护、隐私数据最小披露；生产级外部发布、删除、支付等应按风险审批。
5. **保留退出路线**：Harness、Taskboard、Gateway 任一模块可停用或替换；共享 Git 工件和标准接口仍可被其他 Agent 消费。备份包括 Git 重要 refs、关键状态数据库/日志和配置版本。

## 11. 开发阶段与资源部署策略

**阶段 P0：保留与冻结**。以本卷为平台总纲，以 V1.3 三卷为 M2 专项基线；读取现有 V4.1/V4.2 两个 Draft PR 和云桥 V3.4-candidate 真实状态。整理保留/改造/暂缓清单，不修改现有生产资产。

**阶段 P1：统一执行通路**。先用已通的云端 MCP 复用现有 Bridge；在零刻隔离环境部署最小 Worker（出站注册、心跳、领取、回传），通过 ChatGPT/Gateway 真实调用本地 Buddy，再验证本地对云端委托。GCP 约 1GB 内存的实例只保留轻量服务，不将完整 Harness Web 与构建链强塞到生产桥接机。

**阶段 P2：Git 协作账本**。优先复用旧 WorkBuddy Git Adapter，修复 V1.3 ACK/Gap、正式 Schema、软 CLAIM 和投影写权限；实现 Markdown 文件版本/对账/交付，并跑真实 Git 双身份试验。不要因上 Harness 才允许 Git 自治。

**阶段 P3：Harness 与管理组件**。零刻隔离安装固定版本 Harness、Taskboard、Git/Markdown 插件。先验证兼容、界面、SDK/MCP 与权限；必要时定制小型 Factory Adapter / Git-MD Ledger Adapter，不预设必须另建重型 Controller。

**阶段 P4：三模式验收**。在相同 Registry、Git 证据和执行适配器上分别跑 M1、M2、M3。模式切换保留在途事实。验收达标才推广至双工厂、再逐步扩展十大工厂。

**阶段 P5：无人值守试运行**。经授权开展 24 小时真实任务、故障注入、重启恢复、成本与吞吐审计；对比计划触发/实际唤醒、独立读回、孤儿风险、消息积压、失败恢复和真实产出。定时模型或平台失效不应被模拟定时脚本伪称为成功。

## 12. 三模式最小可重复验收

| 实验 | 场景 | 必要证据 | 尚未完成时状态 |
|---|---|---|---|
| M1-E01 中央编排 | 中央指定三个任务，Harness 通过 Adapter 派发到获授权 Buddy，查询状态、实际测试、回读交付 | task/attempt/runner ID、实际起止、Commit、测试、回读 | NOT_VERIFIED |
| M2-E01 Git自治 | 两 Agent 自主发现缺口、软 CLAIM、消息、ACK、独立产物、协商并合并；涵盖漏醒、重复与 Gap | 两个真实身份、消息 SHA、per-recipient ACK、PR/结果、恢复日志 | NOT_VERIFIED |
| M3-E01 混合协作 | 中央设目标与授权，Agent 自主开子任务协商，指定集成者合法验收/交付 | Policy 版本、子任务证据、协商记录、集成树与真实测试 | NOT_VERIFIED |
| X-E01 双端互联 | ChatGPT→零刻 Buddy 与零刻→云端 Buddy 各执行一次，查询、断线恢复 | 不同节点运行证据、job_id、实际状态、结果哈希 | LOCAL_ROUTE_NOT_VERIFIED |
| X-E02 故障隔离 | Gateway 离线但 Git 自治继续；Git 暂不可用时无副作用研究继续；取消未知不盲重投 | 并行任务连续性、UNKNOWN/ORPHANED 状态、对账 | NOT_VERIFIED |
| X-E03 文档集群 | Markdown 双修改、版本冲突、回读、ACK、缺失/重复对账与正式交付 | 来源与目标 SHA、HEAD 条件写、独立回读、冲突记录 | NOT_VERIFIED |

最低验收规则：有真实证据才报 PASS；一个完成模式不能代替另外两个；一条通道成功不证明另一条成功；已提交 PR 不等于已合并；测试在旧 Commit 上通过不等于新代码通过；没有真实权限探针不能声称强隔离。

## 13. 代码资产继承与变更控制

现有工程资产以历史身份保留：Agensh-Lite V1.3 PR #3 是已批准设计基线的 Draft 文档交付；V4.2 Codex Controller PR #1 与 WorkBuddy Adapters PR #2 仍是未合并的实验代码。首期优先复用 Git 存储、不可变事件、SHA 回读、Runner、Provider Adapter、故障诊断与 CLI；旧强租约/全面阶段验收仅在 M1 或特定受保护操作中按需使用，不能默认成为 M2 普通软 CLAIM 的硬门槛。

对任何组件更换都执行：源版本与适用场景确认→独立测试环境→核心正反例→回读→切换记录与回滚。未经用户批准，不自动合并旧 PR、不改生产定时任务、不切换 GCP 模型、不改变凭据，不往正式主分支写入。

## 14. 开放问题、风险和下一项决策

1. **零刻本地执行权**：尚未通过本轮工具确认本地终端是否可远程调用；必须建立经授权的出站 Worker 才能闭环。
2. **Gateway 部署方式**：优先复用已有云桥；独立服务与否取决于 GCP 内存、可靠性和隔离压测，不预先设强架构。
3. **Taskboard 适配**：要验证独占认领与 M2 Soft CLAIM 能否隔离，否则只用于 M1 或只读看板。
4. **Git 权限**：正式分支保护、Agent 独立凭据与并发写保护未完整核验，实施前应验证。
5. **旧 V4.2 Ledger 的 Gap 缺口**：简单单调时间游标不足以证明连续 ACK；旧简化回执与七类冻结 Schema 不同，必须增加兼容层及真实负例。
6. **运行可靠性**：云桥健康与短任务成功已取得部分证据，不等于 24h 长时稳定或跨端恢复已验收。
7. **三模式策略切换**：先以明确定义的配置和审计事件试验，后再决定是否产品化为图形配置 UI。

**最终架构裁决**：统一平台，不统一所有项目的组织方式；统一事实、权限、资源和证据边界，不强制统一任务发现与协作过程。FactoryOS 必须既能支持中央精细编排，也能支持 Agensh 自组织蜂群，还能按业务性质混合使用。技术组件是可替换的能力实现，真实 Git 证据和项目授权不能被任何单一模型或插件替代。

## 附录 B：审计状态词

- DESIGN_SUPPORTED：设计上允许、组件边界明确；不代表存在可运行代码。
- IMPLEMENTED_PARTIAL：存在相应源码或功能，但范围/兼容性有限。
