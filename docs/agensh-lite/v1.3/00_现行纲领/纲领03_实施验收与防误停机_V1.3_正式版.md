# 第三卷｜Agensh-Lite 实施、验收及防误停机原则 V1.3 正式版

> **验收基准**：不是每一轮按时打卡、每篇字数整齐，而是**真实任务有没有持续推进、事件有没有被正确消费、成果有没有可核验地共享或合并、失败能否局部恢复**。

## 1. 继承微软的实验逻辑，但不误用实验参数

微软论文附录 C 说明：原实验是 ProgramBench 六小时**整体**预算，30 秒/3 秒错峰启动，最后 45 分钟与 5 分钟提醒团队收口，结束时导出共同 Git 提交。附录 B 中 10 分钟 idle detector 用于提醒继续工作，不是“迟到十分钟就停止服务”的处罚器。

**对 Lite 的实际含义**：

- 错峰时间是吞吐优化参数，可以提前、延后、受平台队列影响。**调度精确度不是业务成功判定**。
- 轮次晚醒，如果已有工作仍合法就做；轮次早醒没新事，保留空闲事实并等待下一轮。
- “一轮必须花满若干分钟”“必须一次完成五步”“写完必须压到刚好 500 字”都不是微软的协作要求。
- **真实硬预算/用户明确硬截止仍必须遵守**。如果经过用户批准的实验确实“六小时后禁写”，那是工程授权条件；轮次节拍只是软时间。
- 系统可采用温和的“临近硬截止逐步收口”：少开新工作，多集成已完成的工作，而不是任意丢弃有效的既有工单。

## 2. 五个阶段，保留为检查路线而非僵化流水线

| 阶段 | 目标 | 用事实怎么判断 | 不作为无意义停止条件 |
|---|---|---|---|
| **L0 读验证据** | 确认 Git 仓库、ref、共享消息入口、真实 Agent 凭据权限、原有分支和环境 | Git API 当前回执、清楚的权限与目标；未验证的记录 UNKNOWN | 不强制此刻选正式/实验仓库；不因为某条非关键历史路径404就停掉方案研究 |
| **L1 双 Agent 异步接力** | A 发布真实事件，B 轮询发现、处理、回复；支持漏醒、重复、早/晚醒 | 两个真实身份/轮次、可见 Git SHA、独立 ACK/回读、无重复副作用 | 不为“迟到三分钟”判失败；不强制每轮都有新任务 |
| **L2 自主探索与自组织协作** | Agent 自己发现任务、CLAIM、协商、产出反例/原型 | 有未预排的有效发现与可重放成果；重复范围能够协调 | 不因为两人都认领同题就关闭全部研究 |
| **L3 代码验证与集成** | 自己开发、适当测试、PR、反例复验、合法合并与回读 | 正式代码真实通过适用测试，合并树/提交可回读 | 不强制所有小文档都经历 R2/R3 双重审核 |
| **L4 长时间影子运行** | 多轮真实唤醒、增量读写、跨轮接棒、故障局部恢复 | 持续交付、事件积压、处理延迟、失败恢复、成本和权限记录 | 不以微小时钟偏差、回执长度和某个非关键字段导致全局停机 |

阶段名称保留自 V1.2.1，但完成条件改用**最少可审计的实际事实**，避免“想进入 L1 必须先实现完整大控制器”。具体最小机器约束与用户明确授权仍不可略过。

## 3. 只把五类错误定义为需要真正阻断的事项

1. **权限/安全不可越过**：无权访问、生产仓库/路径非法、凭据或个人隐私泄露风险、用户明确禁止的外部操作。
2. **不可逆副作用不明**：外部写入状态 UNKNOWN 而继续盲写、可能重复扣款/删除/发布；先只读追查。
3. **证据与版本失真**：未实际运行测试却宣称 PASS；旧代码审核套到新代码；把未合并 PR 说成合并完成。
4. **明确硬截止或预算已耗尽**：停止受影响的生产/付费动作，允许合法只读复盘、记录和申请后续授权。
5. **共享权威遭破坏**：主分支受保护写入发生身份/版本冲突，无权强推；阻断这次写操作，其他 Agent 可继续。

其他失败优先**局部记录、重试/改方案/下轮继续**。网络暂断、无消息、目录索引更新慢、Claim 重叠、简单文档过长、个别平台排队不应成为“全工厂 STOP”。

**注意**：在未经验证的仓库规则中，提示词写了“不可写主分支”并不等于平台已实施强权限隔离。无需因此拒绝所有只读探索，但必须禁止把未验证权限说成受保护。

## 4. 必须真实验证的核心情境（不是每轮检查表）

| 编号 | 场景 | 正确行为/验收依据 |
|---|---|---|
| T01 | 计划 10:10，实际 10:13 醒来 | 继续消费有效事件；记录真实开始时间，不因时间差自动 `ABORT` |
| T02 | 提前醒来，暂无新消息 | 可以处理旧工作/探索；没有工作就 `NO_NEW_EVENT`，未来轮次继续 |
| T03 | A 错过一轮，B 产生 3 条事件 | A 下轮识别未消费事件，按稳定 ID 不漏不乱，不把上轮缺席视为已经消费 |
| T04 | 同一事件收到两遍 | 不重复触发不可逆业务动作；保留去重证据 |
| T05 | A、B 同时发布两个软 CLAIM | 双方保留声明并协商；不因此把所有相关 TASK 强制停机 |
| T06 | 私人分支出现消息，公共 ref 没看到 | 标为未正式发布，不能假装对方已收到；经合法途径发布后收件人能看到 |
| T07 | 代码修改/提交成功，但 ACK 写入失败 | 通过目标真实 SHA/稳定 ID 查验，不盲目再次 push/创建文件 |
| T08 | Git 连接失败或历史检索不完整 | 报 `UNKNOWN/CONTEXT_INCOMPLETE`，继续无副作用的其他工作，不能把缺消息当无消息 |
| T09 | Agent 输出 700 字、建议 500 字 | 直接交付有价值内容；下轮可以简短，不进行多轮机械字数统计 |
| T10 | 一个 Agent 报权限拒绝 | 该操作停止并交接；其他合法任务照常进行，不自动更换账号越权 |
| T11 | 两条 PR 各自绿色，合并后破坏接口 | 集成测试应发现并留 FAIL；不得凭作者自报就认为全部集成通过 |
| T12 | 合并目标 SHA 发生变化 | 重新核对当前代码和相应测试证据；旧测试不被机械套用 |
| T13 | WorkBuddy 队列使某任务迟到 | 记录排队延迟并消费有效任务；不把 lateness 当用户撤销任务 |
| T14 | 某轮模型/平台无法发长日志到 Git | 保留未验证状态与恢复指针；短回执说明事实，不伪称已交付 |
| T15 | 明确已授权的真实 `stop_at` 到点 | 停止越期生产写入，但可只读核验、保留既有成果；区分软节拍 |
| T16 | 连续 24h，目录从几十份增长到数千份 | 普通轮次优先增量短事实/检索而非全库扫描；评估实际读取量与成果，不机械按 KB 淘汰任务 |
| T17 | 聊天记录因历史轮次越来越长 | ChatGPT 用户可见最终回执简短；详情在 Git，固定任务指令不追加轮次内容；确认 UI 的实际行为 |
| T18 | 论文机制与我们额外设计冲突 | 保留论文/源码原机制，额外治理标 [ADAPT] 或 [LOCAL]，未经实测和批准不写成必要底座 |

这些是未来实验断言，**尚未在真实定时环境执行**。脚本级模拟不等于定时调度通过。

## 5. 验收证据的最小集合

**默认只需七项**：`run_id`（若平台可见）、执行身份、实际发生时间、任务/事件 ID、执行结果、代码/文件的实际 Git 指针（有产物时）、测试或回读的真实证据/未验证标记。

如果是**纯讨论**，没有 Git 或 Runner 工件，就不强制编造 sha；如实说“仅研究”。如果是**真实外部写入/代码集成**，必须有相应提交/树 SHA 与回读，不能因“轻量”删掉可重复副作用的保护。

典型状态可以用 `DONE / PARTIAL / NO_NEW_EVENT / RETRY_PENDING / BLOCKED_ACTION / UNKNOWN` 等紧凑标签；不要为了状态标签满足模板而忽略正常业务推进。正式机器数据 Schema 如需更新，则按迁移规则处理，不静默混用旧事件流。

## 6. 运营看什么，不看什么

**优先指标**：实际用户目标的可运行成果、有效合并/测试、从事件到首次有用响应的时间、未消费事件积压、重复副作用、可恢复失败、真实成本。

**辅助观察**：定时任务实际唤醒时刻、错峰延迟、模型轮次简报字数、检索量、各平台计量。但这些辅助指标**不能直接当成全局停止线**。

**看板每天/每阶段记录**：已产出什么可运行结果，哪些关键问题被证伪/发现，已发布哪些消息，哪些仍待回应，哪些需要用户授权；不要为增加“工单完成数、Markdown 数、精确按时率”制造无意义工作。

## 7. 极简执行者回执和详细事实分离

ChatGPT 的定时会话按用户观察会累积显示历史，所以定时任务指令**长期不变、尽量短**；每次工作**真正细节只写 Git**，最终只保留一句任务状态和一个证据指针。`不超过200字`若写入模板仅作为写作建议，**不进入校验器、不让模型逐字计数、不以超字数取消提交**。

WorkBuddy 每次是否新会话，以当前真实产品行为为准；也使用相同 Git 交接协议。无论平台怎么呈现，会话文本不能取代 Git 的事实和证据。

## 8. 对现行历史合同的处理

- V1.2.1 七份 JSON Schema、七份原例、F-01～F-07 审计、EX-01～EX-03 细致试验卡及原审计报告**保留原样**；目前属于原规范/候选机检或历史证据，未在本版声称已经部署。
- V1.3 正式设计纲领将这些合同从普通 Agent 每轮必读正文中移出，作为**按需验证的兼容机器合同**；不得因放入附包而失去其对正式结构化写入的效力，不改已存在的活跃消息格式。
- V1.3 已批准为设计纲领；在 L0/L1 对准备启用的消息对象、权限和回读，仍须进行最小必要的真实验证。严密状态机依结构化正式写入的风险与既有合同启用，不强制所有 Agent、所有轮次填写完整机器对象。
- 旧 PR #1/#2 与历史重型方案不因本次文档修订自动合并或重启。仓库、Agent 身份和调度方式未批准前，不写入生产事实。

## 9. 实施与验收结论采用三个独立标签

- `SPEC_REVIEWED`：论文/源码与方案对应关系已审查；不代表运行有效。
- `LOCAL_TESTED`：相应纯函数、Schema 或 Git 仿真得到可复算结果；不代表真实定时模式。
- `REMOTE_VERIFIED`：真实身份、定时唤醒、读写/回读、独立交接、权限和运行证据均符合所需场景。

没有远端证据就保持 `NOT_RUN/UNKNOWN`。新增方案不得凭“论文已在微软跑过”直接把我们自己的 Git+定时实现标为 `REMOTE_VERIFIED`。

## 11. V1.3 四项必要修复的独立验收 [P1-01～P1-04]

以下属于**拟议试验卡**，不等于已经真实运行。继续沿用 L0～L4 阶段，但每个故障只影响对应动作，不把软时刻、文本长度、CLAIM 重叠作为全厂停机门禁。

| 对应整改 | 实验/反例 | 最小可复算通过条件 | 证据等级 |
|---|---|---|---|
| P1-01 契约生效 | 用旧七份 `AGL_LITE_V1_2_1` Schema 验证结构化 TASK/EVENT/MESSAGE/ACK/REVIEW/DELIVERY/RUN；尝试错版本及非法路由 | 七份正例有效；负例被拒；Registry 明确政策/SHA/ref；普通 Markdown 无需强填 Schema；旧流未静默改写 | `LOCAL_TESTED` + 未来 `REMOTE_VERIFIED` |
| P1-02 ACK/Gap | A 发布 E1、E3，延迟 E2；两收件人分别确认；模拟重复与 ACK 中断 | 连续水位停 E1，E2 真实处理后才前进；每人独立 ACK；副作用不盲重放 | `LOCAL_TESTED` + 真实 Git 两轮验收 |
| P1-03 CLAIM/写者 | 两 Agent 软 CLAIM 同题，尝试更新共享 BOARD / 受保护 ref；模拟并发目标 SHA 变化 | CLAIM 并存而系统不停；未授权/旧 HEAD 的正式写入遭真实拒绝；个人成果仍保留 | 真实 Git 身份与权限探针 |
| P1-04 双通道 | **Git 链路**：Agent A 发布，B 下轮接棒；**Bridge 链路**：独立验证健康、认证、执行、结果回收与异常 | 两条通道各有可回读证据；Bridge 不可达时 Git 自主协作可继续；超时且无状态查询时保持 `UNKNOWN` 不盲重试 | 独立远端试验，不得以文档 PASS 代替 |

### 11.1 三个最小真实验证，不引入新的重型仪式

1. **EX-01 Git 跨轮消息**：真实不同 Agent 身份；消息发布 ref 可见、按收件人 ACK 和 Gap 补扫；早/晚醒不丢有效消息。
2. **EX-02 Soft CLAIM 与真实权限**：两人同时探索可继续，未授权公共状态写入确实被 Git 平台拒绝；不能只凭 Prompt 拒绝。
3. **EX-03 组合集成与 Bridge 子试验**：真实 Git base/head/tree、合并后测试和回读；另以真实 Bridge 请求验证端到端能力。二者分别记录，不将单次 HTTP 200 偷换成 Git/业务验收。

Bridge 单独记录 `health_reachable`、`execute_auth_verified`、`result_recovered`、`idempotency_verified`、`status_query_supported`、`scheduler_compatible`，无证据写 `UNKNOWN/NOT_RUN`；**不凭推测补成 PASS**。

### 11.2 建议的复核与晋升边界

- 规范有据、离线测试通过可以给 `SPEC_REVIEWED/LOCAL_TESTED`，但**未进行远端执行时只能标 `REMOTE_NOT_RUN`**。
- V1.3 已获用户明确批准成为正式**设计纲领**，四项 P1 文本映射已完成；它不自动授权任何运行写入。GCP/MCP 的 P1-04 执行能力正独立联调，**不作为此次设计发布门禁**，仍为 `REMOTE_NOT_RUN`。
- 晋升为无人值守运行规范，须先完成 L0 权限与 Git 真实试验；Bridge/MCP 是独立执行通道，可后续单独验收，不能阻断 Git 自组织主线。失败局部标记，不因一个 Bridge 不可达冻结已有 Git 异步通道。
- 必须纠正归因：V1.2.1 已写明调度时刻不是业务 deadline；误把早晚醒或建议字数变成硬停机，是某些历史运行指令/执行反模式，不能简单归咎于旧三卷。
