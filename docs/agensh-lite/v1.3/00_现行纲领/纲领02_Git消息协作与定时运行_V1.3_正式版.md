# 第二卷｜Agensh-Lite Git 协作、事件消费与定时运行协议 V1.3 正式版

> **运行口令**：醒来查事实，自己找有用工作；认领、执行、验证、共享；困难时找伙伴，失败保留证据，下一轮继续。**不因错峰、字数、普通文档缺失而放弃仍可做的工作。**

## 1. 五步循环，是唯一默认业务流程

| 阶段 | 工作要点 | 不要求 |
|---|---|---|
| **Gather** | 看共同目标、自己的未完工作、未处理消息、近期 `FACT/FAIL/CLAIM/PATCH_SUMMARY`；必要时 `grep/unfold` 历史 | 不全文扫目录；不每轮重新读三卷 |
| **Claim** | 发现需要做的事情；给其他 Agent 留简短范围声明，重叠则协商 | 不因为没有中央派单就不能工作；不默认强租约 |
| **Act** | 自主设计、探索、编码、修改自己的分支/记录；必要时寻求帮助 | 不强制每轮做完一整个任务 |
| **Verify** | 做合理范围的自测/反证/检查；明确 PASS、FAIL、UNKNOWN 的事实基础 | 不要求任何小任务都找两名 QA 签字 |
| **Merge/Publish** | 代码经 PR/合法合并；事实、失败、请求、交付进入共享消息或知识流，附证据指针 | 不把聊天中“完成了”算真正交付 |

**一轮到点可以结束在任意阶段**，只要保存可恢复的进展，且未越权。周期结束不是让业务任务失败的理由。Agent 无新任务时可自主发现问题、提出新任务或检查未解决冲突，不能伪造“忙碌”记录。

## 2. 三条通信通道分别保留微软语义

| 通道 | 目的 | 轻量实现 |
|---|---|---|
| **Workspace** | 源码、设计、原型、Issue/PR、合并结果 | Git 个人工作树/分支与共同基线 |
| **Message** | 定向请求、协商、冲突、通知、答复 | Git 唯一文件或不可变事件，带接收者与稳定 ID |
| **Shared Context** | 复用已证实事实、失败、进行中的 CLAIM 与补丁摘要 | 事实短条目 + 可检索历史 + 详情引用 |

**消息和短事实在语义上不同**：消息可指定收件人并期待回应；`FACT/FAIL` 供相关 Agent 自主利用；代码仍通过共享 Git 仓库和 PR 整合。可以用同一 Git 载体保存，但不能把三者全部塞进一份不断增长的 `BOARD.md`。

## 3. 每人写自己的 Markdown；发布不等于改别人的文件

个人可以有 `agents/<agent_id>/...` 和隔离代码分支；其他 Agent 只读原件、可以在自己的记录中引用。公共看板是原始事实的视图，不是多人共编辑的权威笔记本。

**建议的最少文件类型，而非必须照搬的正式目录**：

```text
GOAL.md                           # 用户目标和边界，读
AGENTS.md                         # 很短的共同协作口令，读
agents/<agent_id>/notes/<id>.md   # 个人研究、日志，写本人
messages/<msg_id>.json            # 已发布事件/消息，唯一ID
context/<gist_id>.json            # 短 FACT/OBSERVED/FAIL/CLAIM/PATCH_SUMMARY
code/ or branches                 # 真正源码和PR（可在仓库其他目录）
board/INDEX.json                  # 可重建索引，非权威事实
```

`messages/<msg_id>.json` 表示逻辑位置；具体 Git 仓库、ref、目录和令牌由未来批准的 Registry 决定。**不能因为此处示例就创建新仓库或改现有历史路径。**

**正式发布必须具备“对方可见”这个条件**：A 在自己私有分支写文件，只算 A 的草稿；进入所有相关 Agent 实际读取的共享可见 ref/目录、能回读到提交，才算 `PUBLISHED`。其发布可以由 A 用合法权限直接新增唯一文件，也可以由薄的写入中介发布；**不固定成必须经过中央人工审批**。碰撞由 Git 提交冲突/唯一文件 ID 解决，失败后刷新 HEAD 再试。

消息记录至少能识别 `message_id、author、recipients、kind、task_ref(如有)、source_ref、created_at`；复杂 Schema 对需要机器门禁的操作适用，不强制每条短便笺填满七类状态对象。

## 4. 事件语义统一，唤醒可以是即时或定时

`生产者生成事件 → 可靠写入共享事实 → 接收 Agent 在可运行的下一轮发现 → 自主处理 → 产生后续事件`。

- **事件触发**：微软使用 Gitea/Mattermost listener + durable queue；可较快唤醒，部分通知在工具调用返回时递交。
- **定时触发**：ChatGPT/WorkBuddy 到点检查队列。频率和排队延迟是性能参数，不是消息效力条件。
- **早醒**：检查是否有仍有效的事件；没有则做已有工作/探索/简短 `NO_NEW_EVENT`，让后续轮次接棒，**不停任务**。
- **晚醒**：补收尚未处理的事件；只要业务条件、授权和版本仍有效就继续，**不因 `actual_time != scheduled_time` 跳过**。
- **漏醒/拥堵**：按事件身份从上次可靠水位或重扫窗口补读；不能把漏掉一次运行视作消息已处理。若没有可见事件也不要臆测已收到。

唯一真正的硬时间边界是用户或平台明确批准的生产截止、授权有效期、花费预算/安全条件等。微软六小时实验截止属于**实验预算**，其30秒/3秒的错峰属于启动策略；不移植成我们每轮的硬截止。

## 5. 可靠消费：从微软的数据库状态借用最少语义

微软的 `mini-router/src/state.ts` 以 `(dedup_key, agent)` 去重，并维护 `pending / sending / sent / failed / retrying`、有界退避与启动恢复。Lite 不必一开始实现完整 MySQL，可选 **Git 的不可变消息 + 每人 ACK + 简单 Python 检索/重放** 实现相同的可观测行为。

1. 消息只要真实共享发布，就不得因某轮没处理而消失。收件人各自记录“已看到/已处理”或等效 ACK，不能替其他收件人确认。
2. 每轮只关注**新增/未完/失败重试**事件；为了防止分页、游标错误，保留低成本重叠补扫和稳定身份查重。索引不可用时回退到更完整的只读扫描，不能把“读取失败”当“没有任务”。
3. 同一事件再次出现，优先识别为重复，不重复造成外部副作用；写入结果未知时先读目标，确认已写再补回执。
4. 处理失败可以隔离为单事件 `RETRY_PENDING` / `FAILED`，其他互不相关事件和 Agent 继续运行。超过合理重试后做可见告警/交接，不删除原件，也不让整个系统永久停止。
5. **ACK 表示消费，不是业务验收**；微软 `sent` 是路由器投递记录，不等于真实 PR 合并或 Drive 复制完成。状态应按任务/消息/交付分别解释；但 Agent 不必每轮操作全部状态机。

**没有 Python 时的最低降级**：凭稳定 ID 查看共享消息目录、本人待处理索引和最后一次交接，人工/Agent 记录独立 ACK；不得宣称已经做到数据库级强一致、任意高并发下无丢失或“exactly once”。这需要用 L1 测试证明。

## 6. Shared Context：摘要小、详情可查、Agent 自由研究

沿用微软的五种类型：`OBSERVED / FACT / FAIL / CLAIM / PATCH_SUMMARY`。这是共享协作语言，不等于原有七份 JSON Schema 的全部对象类型。

- 新条目尽量只包含结论、范围、证据指针和必要条件。微软原版普通摘要上限100字符，补丁摘要300字符，**我们将其作为风格参考，不作为“一个字超了即拒绝/反复字数计算”的硬门禁**。
- 大型日志、研究推演、代码、测试保存在各自工件中。读取近期短事实，历史用关键词、任务ID、模块和时间检索，再展开特定详情。
- 避免“完整目录树 → Agent逐个文件全读”。目录与基础元数据可由 Python/Git 查询，Agent 只需看命中摘要；真实必要时可以扩展研究，不设脱离实际任务的固定总 KB 配额。
- `board_read` 的微软原版也可能返回较多信息（近期最多2000条、grep默认最多500条）；它是有限检索，不是“模型永不读爆”的保证。Lite 不应把这些原版数字全部生搬硬套成产品失败条件。
- 对研究任务不隐瞒相关冲突或重大 FAIL；如上下文不足，应标示 `CONTEXT_INCOMPLETE` 并继续可独立完成的其他工作或请求补齐，不编造事实。

## 7. CLAIM、冲突、分工和代码合并

微软的 CLAIM 默认约一小时 TTL，旨在减少重复劳动，并非写权限租约；重叠时 Agent 可相互消息协调。**Lite 优先照搬软 CLAIM 协作**：

- 两人都宣称要研究某部分，可以自主协商拆分，或保留两种探索方法。重复研究带来额外费用但不是逻辑错误；不应导致整个任务池 `BLOCKED_CONTESTED`。
- 共享源文件、正式主分支、生产密钥/发布通道则服从仓库真实权限和条件提交。软 CLAIM 不等于获得越权权限。
- 提交 PR 后根据当前 `main` 进行真实集成；合并被拒时同步最新基线、解决冲突并重验。**不要因原定本轮快结束就跳过可安全完成的合并或把未合并写成已交付**。
- **审核允许自组织出现**：作者自测 + 需要时同事复验和提出反例。对高风险生产、身份、凭据、不可逆操作使用已有的严格授权；常规探索/普通文档不一律强制不同 Agent 双签。

微软实验公开 `REPRODUCE.md` 显示 PR 合并允许零批准并未启用 CI 合并门禁。因此双重强制审查是本项目可选的风险治理，不得表述为微软已运行的普遍制度。

## 8. ChatGPT 和 WorkBuddy 各自的运行适配

**共同启动内容尽量恒定而短**：身份、合法 Git 入口、共同目标/当前共享事实入口、五步循环、写本人文件、回读、失败恢复和简短回执。任务正文与历史只在 Git 中变化；长期定时指令不追加逐轮新内容。

**ChatGPT**：鉴于用户观察同一定时任务会展示历轮内容，默认最终对话只报“任务ID、实际结果、Git指针、异常”。**通常一两句话足矣，不设置 200 汉字精确强拒绝**；不得为了压缩回答重复执行、计算字数、返工三轮。模型中间执行过程能否隐藏，取决于平台 UI 能力，不能靠提示词保证。

**WorkBuddy**：根据用户当前观察，每次唤醒可新开会话；仍然从 Git 交接恢复事实，不把平台临时会话当权威来源。WorkBuddy 运行日志可在自身界面稍详，但真实长文和交付同样放 Git。

**不因 ChatGPT 显示长历史就每次重新读全库；不因 WorkBuddy 新开会话就假设它已理解前轮上下文。**

## 9. 故障恢复的优先级：局部继续、证据先行

| 现象 | 应做 | 不应做 |
|---|---|---|
| 计划10:10，实际10:13 | 正常检查未处理事件、继续 | 无条件整轮取消、永远停用定时任务 |
| 提前唤醒但没有新任务 | 继续本人未完工作，或提示空闲后等待后续轮 | 编造任务、提前预制未来交付 |
| 文章比建议长度长 | 有价值就提交；下次可更精简 | 循环精确计数数轮导致任务超时 |
| 某消息缺失/网络暂不可用 | 标记未知，留记录；后续补读、处理其他可执行工作 | 当成消息已处理，或全项目停机 |
| 对同一任务双 CLAIM | 协商或保留两份候选；共享状态按证据变化 | 一律冻结整个项目 |
| Git push 冲突 | 读最新HEAD，有限重试或交接 | 覆盖别人提交、隐式换仓库 |
| 提交超时、ACK丢失 | 先按稳定ID/目标只读查重，再补ACK | 再创建第二份不可逆副作用 |
| 当前代码测试失败 | 保留失败与候选，修复后再测试 | 写PASS或强行合并受保护分支 |
| 某 Agent 没凭据 | 只让相关写动作阻断，可自主做授权范围内研究 | 通过其他账号绕过权限，或把全蜂群停掉 |
| 真实用户硬截止已到 | 禁止越期生产写；可只读审计及保存获准草稿 | 把软轮询时差当硬截止，或无授权继续生产 |

**失败可以是一份有价值的 `FAIL` 记录；只有安全或事实不可判的相关操作需要硬阻断。**

## 10. 最小 Python 与机器契约边界

无需新建中央调度器。首期 Python 只做：消息按目标/收件人过滤、去重和可重放读取；生成短事实索引与检索；检测必要的 Git 身份/版本/路径；核对写入回读和已有 Runner 证据。某些动作能由 Git 原生 API 做就不另造数据库。

**V1.2.1 七类 Schema 的处置**：已从 V1.2.1 第二卷 §21 提取并附在 `03_V121机器契约留存/`，其 `schema_version` **保持 `AGL_LITE_V1_2_1`**。V1.3 不发明与之竞争的 Wire Schema：在尚未批准独立迁移前，结构化对象继续遵守旧合同；普通短摘要/探索 Markdown 可不做结构化对象。对象与场景适用关系见§12。不能“文字说 V1.3 已简化”却偷偷重写旧数据，亦不能强制普通 Agent 每轮把七种对象全生成一遍。

只有要写受保护 ref、真实执行不可逆操作、或者声称已完成业务验收时，才必须提供匹配风险的真实机器证据；一般研究和交流允许简化结构。

## 11. 最简一轮示例（说明性，不是固定路径）

```text
A 在一次定时轮次：读取未完任务和新增FAIL → 自主完成一个功能修复 → 本地自测 → 自己的分支提交 → 发布“已修复/请复验”事件 → 短回执。
B 在下一次合格轮次：读取新增请求 → 自己决定是否接手/商量 → 复验发现反例 → 发布FAIL和复现 → 不修改A的原日志。
A 下一轮：读取FAIL → 修正 → 重新自测 → 更新PR。
合格集成 Agent：以最新真实代码/当前合并基线测试并合法合并，回读确认。
```

如果某次轮询早/晚几分钟，以上逻辑不变；如果测试/合并失败，失败分支留存，其他 Agent 继续。

**源依据**：论文 §2.1–§2.3、Appendix A/B/C；官方 `prompts/agents.txt`、`board-service/{shared_lessons.py,main.py,unfold.py,gquery.py}`、`mini-router/src/{state.ts,dispatcher.ts,board_client.ts}`、`REPRODUCE.md`。具体 1:1 差异在独立对照报告中逐项列明。


## 12. 机器契约的唯一生效表 [P1-01]

**本节已作为 V1.3 正式设计规则生效，但没有授权运行写入。** 七份 Schema 继续沿用 `AGL_LITE_V1_2_1`，不新增 `AGL_LITE_V1_3` Wire Schema，也不静默改写旧流。正式写入前，必须由已批准 Registry 锁定仓库/ref/root、`policy_version`、Schema 包 SHA 和写入身份；未确认 Registry 时仍可研究与生成草稿，但不得写入正式共享状态。

| 对象或用途 | V1.3 兼容机器合同 | 最小适用边界 |
|---|---|---|
| TASK | `task.schema.json`，`AGL_LITE_V1_2_1` | 正式任务对象写入与状态推进；个人待办笔记不是 TASK |
| EVENT | `event.schema.json`，同上 | 进入共享事件流、正式状态重放的事件；`event_type → target_kind` 路由守卫继续有效 |
| MESSAGE | `message.schema.json`，同上 | 需要可靠投递与 ACK 的正式定向消息；聊天摘要不是正式 MESSAGE |
| ACK | `ack.schema.json`，同上 | 每收件人 `SEEN_ACK/PROCESSED_ACK/BLOCKED_ACK`；简短回复不等于 ACK |
| REVIEW | `review.schema.json`，同上 | 声称已通过正式审查/发布门禁的结构化证据；普通同行建议可写 Markdown |
| DELIVERY | `delivery.schema.json`，同上 | 正式目标写入状态，`VERIFIED` 必须有真实回读且哈希匹配 |
| RUN | `run.schema.json`，同上 | 需要证明实际轮次或执行环境的结构化运行记录；可见短回执不是 RUN |
| 个人研究笔记、FACT/FAIL 摘要、普通文档 | 无须伪造以上七类对象 | 短内容 + 可检索详情指针；若承担正式消息/状态用途，应先转为对应结构化对象 |
| Bridge 委托请求/响应 | **尚无获批准的新 JSON Schema** | 不混入旧事件流假装原生 EVENT；沿用平台实有接口，提交/确认后才发布正式记录；见§15 |

原七份 Schema、正例及 V1.2.1 第二卷 §22～§28 的跨对象守卫仍是**正式对象的兼容基线**。即便 JSON Schema 校验 PASS，真实权限、引用存在、跨对象状态转换、读取确认仍须由适用的机械守卫判断。此规则不要求模型每轮全文加载 Schema，只要求真实写入入口进行校验。

**版本迁移条件**：若未来想改变字段或简化 Wire Schema，必须另起新版本、公布对象映射、迁移/兼容读策略、正反例及回退方案；旧与新数据若未经兼容验证不得在同一个活跃流静默混写。

## 13. 消息、ACK 与连续游标的四个不可省略不变量 [P1-02]

微软 `mini-router/src/state.ts` 的去重、队列、游标及恢复语义，在 Git 载体下需以下可机检原则。它们**只约束消息处理完整性，不要求每轮轮询执行整套审核流程**。

1. **独立身份与独立 ACK**：共享消息的 `message_id` 和 `idempotency_key` 稳定；每个 `(message_id,recipient_id,ack_type)` 独立去重，A 的确认不能代替 B。相同事件 ID/业务键而内容 hash 不同须标记冲突并隔离，不能覆写历史。
2. **连续水位不跨 Gap**：如果某条有序流保证了单一发布者、递增且连续的 `stream_seq`，则每收件人每条流分别维护 `contiguous_cursor`；例如 E1、E3 已处理而 E2 缺失，水位最多到 E1。E2 处理并有可回读 ACK 后才可推进 E3。**没有可证明连续序号的流必须用稳定身份枚举差集，不允许拿最大时间戳或最大文件名充当水位**。
3. **确认与业务完成分离**：`SEEN_ACK` 仅证明收到，`PROCESSED_ACK` 证明该消息已完成响应/处理，`BLOCKED_ACK` 保持待处理或有据转派；都不自动等于 TASK 完成、PR 合并、质量验收或外部 `DELIVERY.VERIFIED`。只有 ACK 真正写 Git、独立回读之后，才能由受控投影推进连续水位；投影可重放，不是原始事实。
4. **不确定结果先查再动**：Git/Bridge/Drive 等存在副作用的动作使用稳定 `operation_id`，超时或 ACK 丢失先对账已存在的业务结果，不能盲重放。有限重试用原业务身份，失败保留原事件与 Gap 并局部告警，不为了指标好看跳过未处理消息。确需豁免/重新指派须有可审计批准记录。

**最低验收反例**：双收件人不共享 ACK；E1/E3 已 ACK 但 E2 缺洞不推进水位；重复交付不重复副作用；相同 ID 不同正文被隔离；先发生外部写入后 ACK 失败不自动再执行。测试通过的是机械实现而不是 AI 口头描述。

## 14. Soft CLAIM 不等于正式共享状态写权限 [P1-03]

- **自主探索仍开放**：每人可对同一主题发布软 CLAIM，彼此通知、协商或分别产出候选；只要不冒充正式状态，不因冲突把全局任务置停。
- **正式共享投影必须有受控写者**：`board/BOARD.md`、任务状态投影、连续 `cursor`、正式集成目标不能任意 Agent 直接互相覆盖。按真实 Git 权限和批准的写入策略，采用唯一当前有效写者或串行条件写；每次提交检查目标最新 HEAD，失败时刷新并重新计算，不能强推覆盖。
- **事实与投影分开**：原始消息、CLAIM、ACK、测试证据由各 Agent 在各自授权位置独立写入；公共 BOARD/index 是从不可变事实生成的可重建视图，不以最后写入者为真。
- **强身份必须实测**：Prompt 约定、目录 `allowed_paths`、本地锁不等于仓库侧的权限隔离；普通 GitHub 仓库也不天然支持按路径限制每个令牌。实际保护行为未验收前不得宣布强权限已成立。
- **拒绝只影响对应写入**：若某次提交存在并发冲突或证据不足，拒绝那次正式状态更新；相关 Agent 仍可研究、提交个人工件、请求协调。此处**不恢复完整在线强租约系统**。

## 15. Git 自治与 GCP → WorkBuddy 直接委托两种执行通道 [P1-04]

### 15.1 原生 Git 异步通道（默认）

`Git 共享事件/任务 → 合格 Agent 定时轮询或即时读取 → 自主 CLAIM/Act/Verify → 独立工件 → 公布新事件/证据`。无须经过中心 Agent；正式任务对象遵守§12～§14。

### 15.2 GCP Bridge 直接委托通道（可选、暂缓验收）

**发布范围说明**：GCP/MCP 桥接仍在独立联调；本节保留未来适配设计，**不构成本次 V1.3 设计发布门禁**，更不构成任何已完成工具调用的证据。接口、鉴权、任务幂等和定时任务兼容性均需以后单独验收。

当明确的编码/执行任务适合直接交给 WorkBuddy 时，调用者可经 **GCP Bridge → WorkBuddy** 提交请求。当前**仅按已讨论的接口设计**登记：`POST /v1/execute`（字段 `prompt`、可选 `conversation_id`、`timeout_ms`；预期响应含 `result`），`GET /health`（预期状态）；**实际部署、认证成功、服务端任务状态查询、去重能力，以及 ChatGPT 定时任务中可调用，均标记 `UNVERIFIED`**。不得将 `GET /health` 成功当作 `execute` 成功；不得把预期 `result` 当作目标 Git 已完成交付。任何敏感令牌只留在受限凭据系统，不进入 Git/Markdown/输出。

**未来启用时的最低可信执行过程（非当前已运行协议）**：发起前必须持久化唯一委托请求和稳定 `operation_id`（可采用经批准的 GCP 受控任务队列或 Git，不强制每次短期直接委托先经 Git 中转），并明确是否允许副作用；通过真实授权执行一次调用；收到响应后核对实际产物与 Git SHA 或其他获准目标的回读证据；正式工程交付与关键审计证据按规则归档 Git。若接口无法识别 `operation_id`，不能假设服务端幂等。**网络超时或连接中断时先记 `UNKNOWN`、查询/对账真实结果；查询能力缺失时保留 `UNKNOWN` 并停止该委托的盲重试**，允许其他独立任务继续。未知的轮次不制造第二个副作用。

Bridge 不当全局任务分配器，不强制所有 Agent 走桥接，不改变现有 Git 事实权威。若未来支持 `get_status` 或异步任务 ID，先在独立接口能力测试中证明，再补充到运行协议；现阶段**不把它写成已实现能力**。
